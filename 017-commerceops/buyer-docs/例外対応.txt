CommerceOps — EC受注・ピッキング・梱包・出荷・返品管理
操作説明書: 例外対応（例外キュー）

対応バージョン: 1.0.0
作成日: 2026-09-30


【この説明書について】
  欠品、棚にない商品、住所の不備、取込データの食い違いなど、人の判断が必要な
  できごとを管理する「例外キュー」の使い方と、種類ごとの対応手順を説明します。

  ・画面名・ボタン名は「」で示します。
  ・関連する説明書: 「注文CSV取込.txt」「在庫引当.txt」


■ 1. 例外キューとは

  注文や倉庫の作業で起きた「人が判断すべきこと」を 1 か所に集め、
  対応が終わるまで記録・管理する画面です。

  CommerceOps は、次のようなことを自動では行いません。
  代わりに例外として登録し、担当者の判断を待ちます。
    ・注文のキャンセル（取込データが取消を示していても）
    ・注文の数量を減らすこと（在庫が足りなくても）
    ・在庫数を減らすこと（ピッキングで商品が見つからなくても）
    ・作業が進んだ注文の内容を、取込データで上書きすること

  例外は、状態が「解決」か「対応不要」になるまで「未解決」として残ります。
  メニュー「例外キュー」の横に、未解決の件数が表示されます。


■ 2. 例外の種類と重要度

  種類              重要度  作られるとき
  欠品              中      引当で在庫が足りなかったとき
  Short Pick        高      ピッキングで「棚にない」と報告されたとき
  在庫不整合        高      同上（その棚の在庫が「調査中」になる）
  住所不備          中      送付先の氏名・郵便番号・住所に不備があるとき
  強制梱包          高      全数を検品する前に梱包を強制完了したとき
  返品差異          中      返品の到着数が申請と違う・想定外の品物がある
  追跡番号重複      中      追跡番号 CSV 取込で番号が重複していたとき
  取込競合          高      注文 CSV の取込で競合・取消候補があったとき
  キャンセル棚戻し  中      ピック済みの商品がある注文・Wave を取消したとき
  現場報告          中      スマホ作業モードから報告されたとき
                            （「安全上の問題」の報告は 高）
  その他            ―      現在のバージョンでは、自動で作る処理はありません

  ・重要度は「高」「中」「低」の 3 段階です。現在のバージョンで自動で作られる
    例外は「高」か「中」です。
  ・どの種類も、7 章に対応手順があります。


■ 3. 一覧の画面

  メニュー「例外キュー」を開きます。

【タブ】
  未解決（未対応と調査中）/ 未対応 / 調査中 / 解決 / 対応不要 / すべて
  最初は「未解決」が表示されます。

【絞り込み】
  種類      括弧の中に未解決の件数が表示されます。
  重要度    高 / 中 / 低
  担当      すべて / 自分 / 未割当
  検索      例外番号・注文番号（完全に一致するもの）、件名（一部が一致するもの）

【一覧の列】
  重要度 / 件名（下に例外番号 EXC-000001）/ 種類 / 状態 /
  関連（注文番号・出荷作業・返品・荷物・SKU・倉庫）/ 担当 / 発生
  ・未解決のものが先に、重要度の高い順、新しい順に並びます。
  ・件名を押すと詳細の画面が開きます。

  「ホーム」の「例外（未解決）」「例外（重要度 高）」「欠品」のタイルからも
  開けます。


■ 4. 詳細の画面と基本の操作

  詳細の画面には、次の欄があります。
  「内容」
    関係する注文・出荷作業・Wave / タスク・荷物・返品・取込・商品・
    倉庫 / ロケーションと、例外ごとの詳しい情報が表示されます。
    注文・Wave・荷物・返品・取込は、押すとその画面を開けます。
    詳しい情報の一部は英字の項目名で表示されます（意味は 11 章）。
  「担当」
    担当者を選びます（未解決の例外のみ）。
  「調査中の在庫」
    在庫不整合の例外で、在庫の処理を行う欄です（7-3）。
  「対応履歴」
    発生・状態の変更・担当変更・コメントを、日時と実行した人とともに
    記録します。

【4-1. 状態の流れ】
  未対応 →「調査中にする」→ 調査中 →「解決」または「対応不要」→ 解決 / 対応不要
  ・未対応から、直接「解決」「対応不要」にもできます。
  ・解決・対応不要の例外は「再オープン」で未対応に戻せます。

【4-2. 調査中にする】
  対応を始めたら、上部の「調査中にする」を押します（未対応のときだけ表示）。
  ほかの人に、対応中であることが分かります。

【4-3. 担当者を決める】
  「担当」の欄で担当者を選びます。「未割当」を選ぶと担当を外します。
  ・担当者に選べるのは、例外に対応できる権限（Owner、Operations Manager）を
    持つ有効なユーザーで、その例外の倉庫を担当している人です。
  ・メニュー「作業割当」の「例外対応（未解決 ○）」の欄でも、まとめて担当者を
    割り当てられます。
  ・一覧の「担当」で「自分」を選ぶと、自分の担当だけを表示できます。

【4-4. コメントを記録する】
  「対応履歴」の下の入力欄（「調査内容などを記録（個人情報は書かない）」）に
  入力して「記録」を押します。1,000 文字まで入力できます。
  お客様の氏名・住所・電話番号などの個人情報は書かないでください。

【4-5. 解決にする】
  1. 上部の「解決」を押します。
  2. 「例外を解決」の画面で「解決方法」を選びます。
       修正済み / 在庫を調整 / 再引当・再割当 / 住所を修正 /
       お客様に連絡済み / 重複 / その他
  3. 必要に応じて「メモ」を入力します。「その他」の場合は「メモ（必須）」です。
  4. 「解決にする」を押します。
  ・解決方法は必ず選びます。
  ・「自動解決」は選べません（システムが自動で解決したときに表示されます）。

【4-6. 対応不要にする】
  対応の必要がないと判断した場合に使います。
  1. 上部の「対応不要」を押します。
  2. 「理由（必須）」に、なぜ対応が不要かを後から分かるように書きます
     （2 文字以上）。
  3. 「対応不要にする」を押します。

【4-7. 再オープンする】
  解決・対応不要にした例外で、上部の「再オープン」を押すと未対応に戻ります。
  ・同じ内容の新しい例外がすでに未解決で残っている場合は、
    「同じ内容の例外 EXC-○○○○○○ が未解決です。そちらで対応してください」
    と表示され、再オープンできません。新しい方の例外で対応してください。


■ 5. 自動で解決する例外

  次の例外は、原因が解消すると自動で「解決」になります。
  解決方法は「自動解決」と表示され、メモに理由が残ります。

  欠品
    ・引当で注文の全部の数量をそろえたとき（自動解消: 全量引当）
    ・注文をキャンセルしたとき（自動解消: 注文キャンセル）
    ・明細取消で、足りない数量がなくなったとき（自動解消: 明細取消で不足なし）
  住所不備
    ・注文の「住所変更」で送付先を直したとき（自動解決: 送付先を修正）
    ・再検証で住所の問題がなくなったとき（自動解決: 再検証で住所の問題なし）
  Short Pick
    ・「Fulfillment」の画面で「Short を解決」を実行したとき
      （別倉庫へ再割当 / バックログへ戻す）

  上記以外の例外は自動では解決しません。対応が済んだら、担当者が「解決」
  または「対応不要」にしてください。


■ 6. 同じ内容の例外は 1 件にまとまります

  同じ原因の例外が未解決のまま残っている間は、新しい例外を作らず、
  今ある例外の内容を更新します。まとまる単位は次のとおりです。
    欠品                1 つの注文につき 1 件
    Short Pick          1 つの出荷作業につき 1 件
    在庫不整合          1 つのロケーションの 1 つの SKU につき 1 件
    住所不備            1 つの注文につき 1 件
    強制梱包            1 回の梱包作業につき 1 件
    返品差異            1 つの返品につき 1 件
    追跡番号重複        配送会社と追跡番号の組み合わせごとに 1 件
    取込競合            1 つの注文につき、競合と取消候補でそれぞれ 1 件
    キャンセル棚戻し    1 つの注文（または 1 つの Wave）につき 1 件
    現場報告            1 回の報告につき 1 件（二重送信は 1 件にまとめます）
  解決・対応不要にした後で同じことがまた起きた場合は、新しい例外が作られます。


■ 7. 種類ごとの対応手順

【7-1. 欠品】（重要度 中）
  作られるとき
    引当で、注文の数量の一部または全部を確保できなかったとき。
  件名の例
    欠品: SO-000123（不足 2 個）
  内容の見方
    明細（sku と short = 足りない数）、remainingUnits（足りない数の合計）、
    splitCandidates（他の倉庫で引当できる数。warehouseCode = 倉庫コード、
    units = 個数）
  自動で解決
    する（5 章）
  対応手順
    1. 「注文」を押して注文の画面を開き、「在庫引当」の欄の「判断の説明」を
       確認します。
    2. 状況に合わせて、次のどれかを行います。
       ・他の倉庫に在庫がある
           → その倉庫の行の「この倉庫から引当」
       ・入荷を待つ
           → 例外を「調査中にする」、入荷予定をコメントに記録。
             入荷したら「在庫・商品」で「入荷を登録」し、「引当」画面の
             「引当を実行」（または注文の画面の「ルールで引当」）
       ・そろった分だけ先に送る
           → 「揃った分を先行出荷」（残りがそろうまで例外は未解決のままです）
       ・お客様と相談して数量を減らす
           → 「明細取消」
       ・注文をやめる
           → 「キャンセル」
    3. 全部の数量がそろう、キャンセルする、などで例外は自動で解決します。
  注意
    在庫が足りないまま手動で「解決」「対応不要」にすると、次の「引当を実行」で
    その注文をもう一度試し、足りなければ新しい欠品の例外が作られます。

【7-2. Short Pick】（重要度 高）
  作られるとき
    ピッキング担当者が、スマホ作業モードの「棚にない（Short）」から
    Short を報告したとき。同時に「在庫不整合」（7-3）も作られます。
  件名の例
    Short Pick: F-000045
  内容の見方
    出荷作業、Wave / タスク、商品、倉庫 / ロケーション、
    reasonCode（Short の理由。11 章）、shortQty（Short にした数）
  影響
    ・Short が解決するまで、その出荷作業は梱包できません。
    ・注文はキャンセルされません。
  自動で解決
    する（「Short を解決」を実行したとき）
  対応手順
    1. メニュー「Fulfillment」を開き、「絞り込み」で「Short あり」を選びます。
       （例外の画面の「（Fulfillment 一覧で対応）」からも開けます）
    2. 対象の出荷作業の「Short を解決」を押します。
    3. どちらかを選んで「実行」を押します。
       ・「別の倉庫（または同じ倉庫の別ロケーション）から再割当する」
           「再割当する倉庫」を選びます。引当できた分の出荷作業が作られます。
           引当できなかった分は、欠品の例外になります。
       ・「バックログへ戻す（入荷後などに改めて引当）」
           足りない分を、引当を待つ状態に戻します。後で引当します。
    4. ピック済みの商品は、元の出荷作業のまま梱包・出荷できます（分割出荷）。
    5. Short Pick の例外は自動で解決します。棚の在庫は「在庫不整合」の例外で
       確認します（7-3）。
  補足
    お客様と合意して数量を減らす場合は、注文の画面の「明細取消」も使えます
    （作業中（Wave に入った後）の数量は取り消せません）。

【7-3. 在庫不整合】（重要度 高）
  作られるとき
    Short Pick の報告で、そのロケーションの在庫が「調査中」になったとき。
    調査中の数は引当に使われなくなります（OnHand は減りません）。
  件名の例
    在庫不整合の可能性（Short Pick 2 個）
  内容の見方
    商品、倉庫 / ロケーション、heldQty（調査中にした数）、reasonCode、
    「調査中の在庫」の欄（在庫 / 引当 / 調査中 / 引当可能）
  自動で解決
    しない
  対応手順
    1. 「倉庫 / ロケーション」の棚と、その周りを確認します。
    2. 詳細の画面の「調査中の在庫」の欄で数量を入力し、結果に応じて押します。
       ・見つかった        →「見つかった（引当可能に戻す）」
       ・見つからなかった  →「紛失確定（在庫を減らす）」
       一部だけ見つかった場合は、数量を変えて 2 回に分けて操作します。
       （在庫を変更できる権限が必要です。Owner、Operations Manager）
    3. 在庫の処理が終わったら「解決」を押し、「解決方法」で「在庫を調整」を
       選んで「解決にする」を押します。
  補足
    「在庫・商品」→「ロケーション別」→「調査中を解消」でも同じ操作が
    できます。その場合も、最後にこの例外を「解決」にしてください。

【7-4. 住所不備】（重要度 中）
  作られるとき
    取込や手動作成の注文で、送付先の氏名・郵便番号・住所がない、または
    郵便番号の形式が正しくないとき。注文は「要確認」になり、引当されません。
  件名の例
    住所不備: SO-000123（郵便番号がありません）
  内容の見方
    注文、コード（SHIP_TO_NAME_MISSING など。11 章）
  自動で解決
    する（5 章）
  対応手順
    1. 「注文」を押して注文の画面を開きます。
    2. 必要ならお客様に確認します。時間がかかる場合は、例外を
       「調査中にする」にしてコメントを記録します。
    3. 注文の画面の「住所変更」で正しい送付先を入力し、
       「変更理由（必須・履歴に残ります）」を書いて「変更する」を押します。
    4. 例外は自動で解決します。他に問題がなければ注文は「引当待ち」になります。

【7-5. 強制梱包】（重要度 高）
  作られるとき
    Packing Station で、全数のスキャン検品が終わる前に、管理者が
    「強制完了（管理者）」で梱包を完了したとき。未検品の分は、目で確認した
    ものとして梱包済みになっています。
  件名の例
    強制完了: F-000045（SO-000123）未検品 1 個
  内容の見方
    注文、出荷作業、明細（sku、scanned = スキャン済みの数、
    required = 必要な数）、理由（強制完了の理由）
  自動で解決
    しない
  対応手順
    1. 出荷確定の前に、箱の中身が明細のとおりか、目で確認します。
    2. 正しければ「解決」を押します（例: 解決方法「修正済み」、メモに確認内容）。
    3. 違っていた場合は、注文の画面の「Fulfillment（出荷作業）」の欄で
       「梱包取消」を押し、理由を入力して「梱包を取り消す」を押します。
       箱を開けて、Packing Station で梱包し直してから「解決」にします。
  注意
    出荷確定した荷物は、梱包取消できません（返品で対応します）。

【7-6. 返品差異】（重要度 中）
  作られるとき
    返品の「到着を登録」で、届いた数が申請の数と違うとき、または
    「想定外の品物・申請より多い場合（任意）」に記入したとき。
  件名の例
    返品差異: RT-000007（数量差 1 件）
  内容の見方
    返品、注文、明細（sku、requested = 申請の数、received = 届いた数）、
    想定外の品物
  自動で解決
    しない
  対応手順
    1. 「返品」を押して返品の画面を開き、届いた現物を確認します。
    2. 必要に応じてお客様に連絡します。
    3. 検品（再販可・破損などの判定）は、実際に届いた数で行います。
    4. 対応が済んだら「解決」を押します
       （例: 解決方法「お客様に連絡済み」）。

【7-7. 追跡番号重複】（重要度 中）
  作られるとき
    「出荷」の「追跡番号 CSV 取込」で「取り込む」を実行したときに、
    同じ配送会社の同じ追跡番号が、ファイルの中で重複していた、または
    別の荷物ですでに使われていたとき。その行は取り込まれていません。
  件名の例
    追跡番号の重複: 000000001001（ヤマト運輸）
  内容の見方
    配送会社（yamato などのコード。11 章）、追跡番号、行（CSV の行番号）、
    使用中の荷物（その番号をすでに使っている荷物の出荷番号）
  自動で解決
    しない
  対応手順
    1. CSV の該当する行と「使用中の荷物」を確認し、どの荷物の番号が正しいかを
       調べます。
    2. 正しい追跡番号を登録します。
       ・荷物の画面（「出荷」→ 出荷番号）の「追跡番号」に入力して「保存」
         （出荷済みの荷物は「訂正理由（出荷済みの訂正に必須）」を入力して
         「訂正を保存」）
       ・または CSV を直して、もう一度「追跡番号 CSV 取込」を行う
    3. 「解決」を押します（例: 解決方法「修正済み」または「重複」）。

【7-8. 取込競合】（重要度 高）
  取込競合には「競合」と「取消候補」の 2 種類があります。
  内容の kind が conflict なら競合、cancel_candidate なら取消候補です。

  （競合）
  作られるとき
    注文 CSV の取込で、作業が進んだ注文（一部でも引当・出荷済み、または
    キャンセル済み）と同じ注文番号で、内容の違うデータがあったとき。
    注文は変更されていません。
  件名の例
    取込競合: SO-000123（作業中の注文と内容が異なります）
  内容の見方
    注文、取込、batchNumber（取込番号）、externalOrderId（外部注文番号）、
    orderStatus（取込時の注文の状態。11 章）、
    changed（変わった項目。例: 送付先, 明細）
  自動で解決
    しない
  対応手順
    1. 「取込」を押して取込の画面を開き、その注文の行を確認します
       （明細の SKU × 数量などが表示されます。住所の詳しい内容は、元の CSV
       ファイルで確認してください。取込の確定から 7 日を過ぎると、取込の画面の
       明細・送付先は表示されなくなります）。
    2. 「注文」を押して注文の画面を開き、今の内容と比べます。
       EC サイト側の注文も確認します。
    3. 必要な修正を、注文の画面で行います。
       ・送付先が変わった      →「住所変更」（出荷前のみ）
       ・数量が減った・商品が取り消された →「明細取消」
       ・注文が取り消された    →「キャンセル」（出荷済みの分は返品）
       既存の注文に商品を追加する、数量を増やす、といった操作はありません。
    4. 修正したら「解決」（例: 解決方法「修正済み」「住所を修正」）、
       修正が不要なら「対応不要」（理由を記入）にします。

  （取消候補）
  作られるとき
    注文 CSV の取込で、キャンセルフラグの列が「取消」を示していたとき。
    注文は自動ではキャンセルされていません。
  件名の例
    取消候補: SO-000123（取込データでキャンセル）
  内容の見方
    注文、取込、kind（cancel_candidate）、batchNumber、externalOrderId、
    orderStatus
  自動で解決
    しない
  対応手順
    1. EC サイト側で、本当にキャンセルされたかを確認します。
    2. キャンセルする場合は、注文の画面で「キャンセル」します
       （出荷済みの商品がある場合は、未出荷の分を「明細取消」、出荷済みの分を
       返品で扱います）。ピック済みの商品があると「キャンセル棚戻し」の
       例外が作られます（7-9）。
    3. 「解決」（例: 解決方法「修正済み」）にします。
       キャンセルしない場合は「対応不要」（理由を記入）にします。

【7-9. キャンセル棚戻し】（重要度 中）
  作られるとき
    ・ピック済みの商品がある注文をキャンセルしたとき
    ・ピック済みの商品がある Wave を取消したとき（「棚戻しを伴って取消」）
  件名の例
    キャンセル棚戻し: SO-000123（3 個）
    Wave取消の棚戻し: W-000012（3 個）
  内容の見方
    明細（sku、qty = 数、location = 戻すロケーション、
    fulfillment = 出荷作業の番号）
  自動で解決
    しない
  対応手順
    1. 明細の表のとおり、ピック済みの商品を元のロケーションに戻します。
    2. 「解決」を押します（例: 解決方法「修正済み」、メモに戻した内容）。
  補足
    ・ピッキングでは在庫の数は変わらないため、システムの在庫は元の
      ロケーションにあるままです。商品を棚に戻すだけで、在庫の調整は
      不要です。
    ・Wave を取消した場合、出荷作業は「Wave待ち」に戻り、次の Wave で
      もう一度ピッキングします。

【7-10. 現場報告】（重要度 中。「安全上の問題」は 高）
  作られるとき
    スマホ作業モードの「例外を報告」から報告が送られたとき（8 章）。
  件名の例
    現場報告: 破損品
    （ほかに ロケーションの問題 / バーコード読取不可 / 商品が見当たらない /
      安全上の問題 / その他）
  内容の見方
    分類（category）、メモ、コード（読み取ったコード）、報告者のロール、
    商品（コードが商品のバーコード・SKU の場合）、
    倉庫 / ロケーション（倉庫を選んだ場合や、コードがロケーションの場合）
  自動で解決
    しない
  対応手順
    1. 内容を確認し、現場で状況を確かめます。
    2. 必要な対応を行います。
       例: 破損品 → 在庫の調整や、破損ロケーションへの移動
             （販売可能なロケーションから破損ロケーションへ移すときは、
             理由の入力が必要です。「在庫引当.txt」4-3）
           ロケーションの問題 → ラベルの貼り直し
           商品が見当たらない → 棚の確認
    3. 「解決」、または対応が不要なら「対応不要」（理由を記入）にします。

【7-11. その他】
  一覧の種類に「その他」がありますが、現在のバージョンでは、この種類の例外を
  自動で作る処理はありません。


■ 8. 現場からの報告（スマホ作業モード）

  倉庫の現場で見つけた問題を、スマホから例外キューに報告できます。
  1. メニュー「スマホ作業モード」の「現場作業」の画面で「例外を報告」、
     または画面下のメニューの「報告」を押します。
  2. 「例外を報告」の画面で「内容」を選びます。
       破損品を見つけた / 商品が見当たらない /
       ロケーションの問題（ラベル・棚） / バーコードが読めない /
       安全上の問題 / その他
  3. 必要に応じて「倉庫（任意）」、「商品またはロケーションのコード（任意）」、
     「メモ（任意・500文字まで）」を入力します。
     メモには、お客様の氏名・住所・電話番号などの個人情報を書かないでください。
  4. 「報告を送信」を押します。
     「報告を送信しました。管理者が例外キューで確認します。」と表示されます。
  ・オフラインのときは送信できません。
  ・Picker・Packer も報告できます（例外キューを見ることはできません）。
  ・ピッキング中に棚に商品がない場合は、ピッキングの画面の
    「棚にない（Short）」から報告します（7-2）。


■ 9. CSV 出力

  必要な権限: Owner、Operations Manager
  1. 「例外キュー」で、タブと「種類」「重要度」「担当」「検索」を
     必要に応じて絞り込みます。
  2. 「CSV 出力」を押し、「文字コード」を選んで「ダウンロード」を押します。
  ・今の絞り込みの条件で、新しい順に最大 10 万件まで出力します。
  ・列: 例外番号 / 種類 / 状態 / 重要度 / 件名 / 注文番号 / 出荷作業 /
        荷物 / 返品 / 倉庫 / SKU / 担当 / 作成日時 / 解決日時 /
        解決方法 / 解決メモ / 無視の理由
    「無視の理由」は、「対応不要」にしたときの理由です。
  ・種類・状態・重要度・解決方法は、英字のコードで出力します（11 章）。
  ・日時は、組織のタイムゾーン（「組織・運用設定」の設定）で出力します。
  ・数式として実行されないよう、「=」などで始まる値には先頭に「'」を付けます。
  ・CSV を出力したことは、監査ログに記録されます。


■ 10. 権限のまとめ

  例外キューの閲覧
    Owner、Operations Manager、Customer Support
    （Picker・Packer は閲覧できません）
  状態の変更・担当者の割当・コメント
    Owner、Operations Manager
  在庫不整合の在庫処理（見つかった / 紛失確定）
    Owner、Operations Manager
  現場からの報告
    すべてのロール
  CSV 出力
    Owner、Operations Manager

  担当する倉庫が決められているユーザーは、その倉庫の例外と、倉庫に関係しない
  例外（欠品・住所不備・取込競合など）だけを見られます。


■ 11. 参考: 画面や CSV に表示されるコードの意味

【種類】
  shortage 欠品 / short_pick Short Pick / address_invalid 住所不備 /
  forced_pack 強制梱包 / inventory_mismatch 在庫不整合 /
  return_discrepancy 返品差異 / tracking_duplicate 追跡番号重複 /
  import_conflict 取込競合 / cancel_putback キャンセル棚戻し /
  field_report 現場報告 / other その他

【状態】
  open 未対応 / investigating 調査中 / resolved 解決 / ignored 対応不要

【重要度】
  high 高 / medium 中 / low 低

【解決方法】
  fixed 修正済み / stock_adjusted 在庫を調整 / reallocated 再引当・再割当 /
  address_corrected 住所を修正 / customer_contacted お客様に連絡済み /
  duplicate 重複 / other その他 / auto 自動解決

【Short の理由（reasonCode）】
  not_found 現物なし / damaged 破損 / wrong_location Location違い /
  qty_short 数量不足 / other その他

【現場報告の分類（category）】
  damaged 破損品 / location_issue ロケーションの問題 /
  barcode_unreadable バーコード読取不可 / missing_item 商品が見当たらない /
  safety 安全上の問題 / other その他

【報告者のロール】
  owner Owner / ops_manager Operations Manager / picker Picker /
  packer Packer / support Customer Support

【住所不備のコード】
  SHIP_TO_NAME_MISSING 送付先氏名がない / POSTAL_MISSING 郵便番号がない /
  POSTAL_INVALID 郵便番号の形式が不正 / ADDRESS_MISSING 住所がない

【配送会社】
  yamato ヤマト運輸 / sagawa 佐川急便 / japanpost 日本郵便 /
  seino 西濃運輸 / fukutsu 福山通運 / other その他

【注文の状態（orderStatus）】
  imported 取込済 / validation_required 要確認 / ready_for_allocation 引当待ち /
  partially_allocated 一部引当 / allocated 引当済 / on_hold 保留 /
  picking ピッキング中 / picked ピック済 / packing 梱包中 / packed 梱包済 /
  partially_shipped 一部出荷 / shipped 出荷済 / cancelled キャンセル /
  return_in_progress 返品対応中 / closed 完了

【「内容」に表示される項目名】
  sku                SKU
  short              足りない数
  remainingUnits     足りない数の合計
  splitCandidates    他の倉庫の分割候補（warehouseCode 倉庫コード、units 個数）
  shortQty           Short にした数
  heldQty            調査中にした数
  reasonCode         Short の理由
  scanned            スキャン済みの数
  required           必要な数
  requested          申請の数
  received           届いた数
  qty                数
  location           ロケーション
  fulfillment        出荷作業の番号
  kind               取込競合の種別（conflict 競合 / cancel_candidate 取消候補）
  batchNumber        取込番号
  externalOrderId    外部注文番号
  orderStatus        取込時の注文の状態
  changed            変わった項目
