CommerceOps — EC受注・ピッキング・梱包・出荷・返品管理
サンプル業務説明（Sample Commerce）


【この資料について】
サンプル組織「Sample Commerce」に入っているデータと、そこで試せる業務の
流れを説明します。実際の画面を触りながら各資料の手順を確かめるための
練習用データです。
登場する氏名・住所・電話番号・メールアドレスはすべて架空です
（住所は「架空町」、メールは @example.invalid）。


■ 1. サンプル組織の作り方（サーバー運用者）

1. 本番用の Owner を作成しておきます（docs/DEPLOY.md）。
2. 次のコマンドを実行します。
   ・開発環境:   npm run seed:sample -w server -- --owner-email owner@example.com
   ・ビルド済み: node dist/scripts/seed-sample.js --owner-email owner@example.com
   ・Docker:     docker compose exec app node dist/scripts/seed-sample.js --owner-email owner@example.com
3. 実行すると、次が表示されます（この表示は 1 回だけです）。
   ・サンプル組織の ID
   ・役割ごとのサンプル用アカウント（Owner / Operations Manager / Picker /
     Packer / Customer Support）のメールアドレスとパスワード
4. --owner-email に指定したユーザーは、サンプル組織の Owner にも追加
   されます。画面右上（狭い画面ではメニュー下部）の組織の切り替えで「Sample Commerce（サンプル）」を
   選んでください。

・すでに Sample Commerce がある場合は何もしません（2 つ目が必要な場合は --force）。
・業務はすべて実際の画面と同じ API を通して作るので、在庫・引当・ピッキング・
  梱包・出荷・返品の数はすべて本番と同じ規則でそろっています
  （作成の最後に整合性チェックを行います）。


■ 2. 本番データとの分離

・サンプル組織は「サンプル」の印が付いた別の組織です。本番の組織とは
  データが完全に分かれていて、互いに見えません。
・サンプル組織の画面の上部には
  「サンプル組織（Sample Commerce）です。本番データとは分離されています。」
  と表示されます。
・実際の注文・顧客の情報をサンプル組織に入れないでください。
・サンプル用アカウントは Sample Commerce 以外の組織には所属していません。
  不要になったら「設定 → ユーザー・権限」で無効化してください。


■ 3. マスター（最初から入っているもの）

【倉庫】
・Warehouse Tokyo（東京倉庫, TKY）… 優先度 10（先に使われる）
・Warehouse Osaka（大阪倉庫, OSK）… 優先度 20
・ロケーション: 各倉庫に A-01〜A-08（ゾーン A）と B-01〜B-06（ゾーン B）、
  自動で作られる DEFAULT（販売可能）・QUARANTINE（返品保留）・DAMAGED（破損）

【販売チャネル】
・Web Store（自社サイト）… CSV で取込
・Marketplace A（モール）… CSV で取込
・Manual（電話注文など、画面から手入力）

【商品】30 SKU
・ベーシック Tシャツ（白・黒・ネイビー × S・M・L）、スウェット パーカー、
  ロゴ マグカップ、キャンバス トートバッグ、ステッカー、ロゴ キャップ、
  リブ ソックス、タンブラー、ドット ノート、ゲルインク ボールペン、
  限定 ピンバッジ（SC-LIMITED）、取り寄せ ブランケット（SC-BACKORDER）
・JAN は店内用の 200 番台（実在の商品のコードと重ならない番号）です。
  バーコードを印刷すれば、スマホのカメラやハンディスキャナで読み取れます。
・在庫は東京・大阪に入荷済み。一部の商品は、次の場面を作るためにわざと
  少なくしてあります。
  ・限定 ピンバッジ … 東京に 1 個だけ（最後の 1 個の取り合い）
  ・マグカップ 青 … 2 個だけ（数量 3 の注文 → 一部引当）
  ・パーカー グレー L … 東京 2・大阪 3（2 つの倉庫に分かれて引当）
  ・キャップ ベージュ … 東京 3（棚の現物不足 → Short）
  ・ソックス L … 最初は 0（後から入荷 → 分割発送）
  ・取り寄せ ブランケット … 0（欠品）


■ 4. 入っている注文と、試せる場面

注文番号（SO-）は作成順に自動で振られます。下の表の「外部注文番号」
（W- / M- / TEL-）で注文一覧を検索すると見つかります。

【CSV 取込と重複・競合】（資料: 注文CSV取込.txt）
・Web Store の CSV で 12 件（W-10001〜W-10012）を取り込み済み。
・同じファイルをもう一度取り込もうとすると拒否されます
  （「注文取込」の履歴で確認）。
・午後のファイルには、同じ内容の注文 2 件（取込時にスキップ）、
  内容が違う W-10003（更新候補。適用していないので元のまま）、
  新しい注文 2 件（W-10013・W-10014）が入っています。
・Marketplace A の CSV で 5 件（M-20001〜M-20005）。
・引当済みの M-20004 を別の内容で取り込み直したため、競合として
  「例外キュー」に入っています（注文は上書きされていません）。
・W-10012 は郵便番号の桁が足りないため「要確認」です。注文詳細で住所を
  直すと、例外（住所不備）が自動で解決します。

【引当・欠品・保留・キャンセル】（資料: 在庫引当.txt）
・最後の 1 個: W-10001（Web Store）と M-20001（Marketplace A）が
  限定 ピンバッジの最後の 1 個を同時に引当しました。片方だけが確保され、
  もう片方は欠品として例外キューに入っています。
・一部引当: W-10005（マグカップ 青 × 3、在庫 2）。
・欠品: W-10006（取り寄せ ブランケット）。
・2 つの倉庫に分けて引当: M-20003（パーカー グレー L × 4）は大阪 3・東京 1
  に分かれ、出荷作業（Fulfillment）が倉庫ごとに 2 つあります。
・保留: TEL-0002（「番地の確認待ち」）。保留を解除すると引当できます。
・キャンセル: TEL-0003（引当後にキャンセルしたので引当は解放済み）。

【Wave・ピッキング・Short】（資料: Waveとピッキング.txt、スマホPick.txt）
・東京倉庫の Wave「午前便」（ゾーン別のタスク）はピッキング済みです。
・ピッキング中に、棚の隣の商品を読んだ誤 scan が記録されています
  （拒否され、数量は増えていません。KPI の誤 scan 率に反映）。
・キャップ ベージュは棚に 2 個しかなく、残りを Short にしました。
  Short の分は在庫から減らさず「調査中」に移り、管理者が大阪倉庫へ
  再割当済みです（大阪の出荷作業がピッキング待ちになっています）。
  → Picker のアカウントでスマホ作業モードを開き、大阪のタスクがある場合は
     実際に scan を試せます（在庫を持つ倉庫の担当範囲に注意）。

【梱包・出荷】（資料: Packing Station.txt、出荷と分割発送.txt）
・午前便の出荷作業はすべて梱包済みで、1 件は 2 箱に分けて梱包しています。
  梱包中に注文に無い商品を読んだ誤 scan（赤い警告）も記録されています。
・ほとんどの荷物は追跡番号を入れて出荷確定済みです。
・W-10010 の荷物と、M-20003 の東京分の荷物は「出荷待ち」のままです。
  → 「出荷」画面で配送会社・追跡番号を入れて出荷確定を試せます
    （追跡番号は架空の番号を入力してください）。
  → M-20003 は大阪分の出荷作業もピッキング待ちなので、2 つの倉庫から
    別々に出荷する流れ（分割発送）も試せます。

【分割発送】（資料: 出荷と分割発送.txt）
・W-10007（Tシャツ・トート・ソックス L）は、ソックス L が未入荷だったため
  「揃った分を先行出荷」で先に 2 商品を出荷し、ソックス L の入荷後に
  2 回目の出荷で完了しています。注文詳細で荷物が 2 つあることを確認できます。

【返品・交換】（資料: 返品交換.txt）
・W-10002: サイズ違いの返品 → 到着（この時点では在庫は増えない）→
  検品で「再販可」→ 在庫に戻りました。
・W-10004: 取っ手が欠けていた返品 → 検品で「破損」（販売可能な在庫には
  戻らず DAMAGED の棚へ）→ 交換品の注文を作成し、引当済みです。
  → 交換品の注文を Wave → ピッキング → 梱包 → 出荷の通常の流れで処理
    してみてください。
・M-20002: 返品の受付だけ（承認待ち）。
  → 「返品・交換」で承認 → 到着 → 検品を試せます。

【例外キュー】（資料: 例外対応.txt）
・欠品（3 件: M-20001・W-10005・W-10006）、住所不備（W-10012）、
  在庫の不一致（キャップ ベージュの Short）、取込の競合（M-20004）が
  未対応で入っています。
  担当の割当・調査中・解決（解決方法の入力）を試せます。


■ 5. 役割ごとに試す

表示されたサンプル用アカウントで、それぞれログインしてみてください
（資料: ユーザーと権限.txt）。
・Owner … すべての画面。設定・バックアップ・監査ログ。
・Operations Manager … 引当・Wave・作業割当・例外・KPI・監査ログ。
  設定（組織・ユーザー・バックアップ）は見えません。
・Picker … スマホ作業モード（タスク・商品確認・報告）。注文の個人情報
  （氏名・住所・電話）は表示されません。
・Packer … Packing Station、出荷、返品の到着。送付先だけが見えます。
・Customer Support … 注文の確認・保留・返品の受付・交換。在庫の調整や
  返品の検品はできません。


■ 6. 注意

・サンプル組織のデータも、組織のバックアップ・監査ログの対象です。
・サンプル組織で試した操作は本番の組織に影響しません。
・スマホ・iPad での操作（カメラ読取・ハンディスキャナ・印刷）は、
  サンプル組織で実機確認を行うのに適しています（docs/RELEASE_CHECKLIST.md）。
