CommerceOps バックアップと復元の手引き
（EC受注・ピッキング・梱包・出荷・返品管理　バージョン 1.0.0）
最終更新: 2026-09-30

この資料は、組織のデータのバックアップと復元について説明します。
前半（第 1 章〜第 14 章）は組織の Owner（オーナー）向けです。
後半の【サーバー運用者向け】は、サーバーを管理してコマンドを実行する方
向けの内容です。
画面名・メニュー名・ボタン名は「」で示します。
例に出てくる組織名・番号・メールアドレスはすべて架空のものです。


■ 1. できること（概要）

【画面でできること（Owner のみ）】
  メニュー「設定」→「バックアップ・復元」で、次の操作ができます。
  ・バックアップをダウンロードする
    組織のデータを 1 つのファイル（.ndjson.gz）にまとめて保存します。
  ・ファイルを検証する
    ファイルが壊れていないか、復元できるかを確認します。
    検証では何も書き込みません。
  ・新しい組織として復元する
    バックアップの内容を「新しい組織」として作成します。
    現在の組織のデータが上書きされることはありません。
  ・復元した組織に切り替える

【サーバー運用者ができること】
  コマンドラインで、定期的なバックアップ、大きなファイルの復元、
  空の環境への障害復旧、整合性チェック、パスワード再設定リンクの発行が
  できます（【サーバー運用者向け】の章）。

【大切なこと】
  1. 復元は必ず「新しい組織」として行います。現在の組織は変わりません。
  2. バックアップファイルには、お客様の氏名・住所・電話・メールが
     含まれます。保管には十分注意してください（第 5 章）。
  3. バックアップファイルの保管（保管場所・保管期間・アクセスできる人の
     管理）は、購入者（お客様）の責任で行ってください。
     CommerceOps が、ファイルを自動で別の場所へ送ったり保管したりする
     ことはありません。


■ 2. 画面の開き方と使える人

  1. Owner のユーザーでログインします。
  2. メニュー「設定」を開き、タブ「バックアップ・復元」を選びます。

  ・この画面を使えるのは Owner（オーナー）だけです。
    Operations Manager など他のロールには、メニュー「設定」自体が
    表示されません（サーバー側でも拒否されます）。
  ・バックアップ・復元の対象は、いま選んでいる組織です。
    複数の組織を使っている場合は、画面上部の組織名のプルダウンで
    組織を切り替えてから操作してください。組織ごとに別のファイルになります。


■ 3. バックアップに含まれるもの・含まれないもの

【含まれるもの】
  ・組織の情報（組織名・タイムゾーン・組織・運用設定の内容）
  ・倉庫・ロケーション、商品・バーコード、販売チャネル、Import Profile
  ・顧客、注文取込の履歴
  ・注文と明細、注文の状態・送付先の変更履歴、保留
  ・在庫（ロケーション別）と在庫の動き、引当と引当の実行履歴
  ・Fulfillment、Wave、Pick タスク・Pick の記録、梱包・梱包の読み取り記録
  ・出荷（荷物）と明細
  ・返品・返品明細・検品結果、交換
  ・例外と対応履歴
  ・返品の検品写真（ファイルそのもの）
  ・監査ログ
  ・注文番号などの採番の状態
  ・ユーザー（氏名・メールアドレス・状態）と権限（ロール・倉庫範囲）
  ・ファイルの情報: 作成日時、形式の版、データベースの版、
    アプリの版、テーブルごとの件数とチェックサム（SHA-256）、
    ファイル全体のチェックサム

【含まれないもの】
  ・パスワード（暗号化した値も含みません）
  ・ログイン中のセッション
  ・招待リンク・パスワード再設定リンク
  ・バックグラウンド処理の予定（ジョブ）
  ・バックアップ・復元の「実行履歴」
  ・ログイン履歴などのセキュリティの記録

  チェックサムは、ファイルの破損・途中切れ・うっかりした編集を
  見つけるためのものです。


■ 4. バックアップをダウンロードする

  1. 「設定」→「バックアップ・復元」を開きます。
  2. 「バックアップをダウンロード」の欄の説明文で、対象の組織名
     （組織「○○」のデータを…）を確認します。
  3. 「バックアップをダウンロード」を押します。
     作成中は「作成中…（件数が多いと数分かかります）」と表示されます。
  4. 終わると「バックアップをダウンロードしました。安全な場所に
     保管してください」と表示され、ファイルが保存されます。

  ・ファイル名の例: commerceops-backup-20261001T003000.ndjson.gz
    ファイル名の日時は協定世界時（UTC）です。日本時間より 9 時間前の
    時刻になります（例は日本時間 2026 年 10 月 1 日 9 時 30 分に取得）。
  ・バックアップ中も業務を続けられます。ファイルの内容は、
    作成を始めた時点のデータで揃っています。
  ・ダウンロードしたら、続けて第 6 章の「ファイルを検証」で
    ファイルが完全か確認することをおすすめします。
  ・ファイルの中身は編集しないでください。編集するとチェックサムが合わず、
    復元できなくなります。ZIP などに圧縮し直さないでください。
    ファイル名は変えてもかまいませんが、拡張子 .ndjson.gz は残してください。


■ 5. おすすめの取得頻度と保管方法

【取得の頻度】
  ・毎日（例: 業務の終了後）に取得することをおすすめします。
    サーバー運用者がコマンドで毎日自動取得する方法もあります
    （【サーバー運用者向け】S2）。
  ・システムのアップデートの前、大量の取込や設定変更の前にも取得します。
  ・保管する世代数を決め、古いものを削除します。
    例: 毎日の分を 14 世代、毎月 1 回分を 12 世代

【保管の方法】
  ・お客様の氏名・住所・電話・メールを含むため、暗号化されたストレージに、
    アクセスできる人を限って保管してください。
  ・メールへの添付やチャットでの共有はしないでください。
  ・サーバーとは別の場所（別のクラウドストレージなど）にも保管してください。
    サーバーやデータベースの障害で、サーバー上のデータと一緒に
    失われないようにするためです。
  ・不要になったファイルは削除してください。
  ・ときどき「ファイルを検証」で、保管しているファイルが
    読み取れることを確認してください。

【データベース全体のバックアップ】
  画面のバックアップは組織ごとのものです。これとは別に、サーバー全体の
  障害に備えて、ホスティング会社のデータベース自動バックアップ
  （ポイントインタイムリカバリなど）と、写真の保存先のバックアップを
  有効にしてもらってください（サーバー運用者に依頼。S1 参照）。


■ 6. ファイルを検証する

  検証は、ファイルを読んで確認するだけです。データベースには
  何も書き込みません。

  1. 「バックアップから復元」の欄の「バックアップファイル」で、
     CommerceOps でダウンロードした .ndjson.gz ファイルを選びます。
  2. 「ファイルを検証」を押します（検証中は「検証中…」と表示されます）。
  3. 結果が表示されます。
     ・「検証 OK」: 形式・件数・チェックサムに問題はありません。
     ・「このファイルは復元できません」: 下に理由が表示されます
       （主なメッセージは第 12 章）。
     あわせて、組織・作成日時・版（データ v1 / アプリ 1.0.0 のような表示）・
     件数（合計の行数・ユーザー数・写真の数）・SHA-256 が表示されます。
     「内訳を表示」を押すと、データの種類ごとの件数を確認できます。

【写真の欠落の表示】
  件数の写真の数のあとに「（うち N 件はバックアップ作成時に保存先に
  ファイルがなく、画像は含まれていません）」と表示された場合、その写真は
  記録だけが入っていて、画像はファイルに入っていません（検証の結果は
  「検証 OK」のままで、復元もできます）。
  バックアップを作ったときに、サーバーの写真の保存先にファイルが
  なかったことを示します。サーバー運用者に写真の保存先の確認を
  依頼してください。

【検証で確認していること】
  ・CommerceOps のバックアップファイル（gzip 圧縮）であること
    （ZIP やほかのファイルは受け付けません）
  ・バックアップ形式の版と、データベースの版が、このシステムと同じこと
  ・各行が読み取れること、データの種類と並び順が正しいこと
  ・テーブルごとの件数とチェックサムが、ファイルの記録と一致すること
  ・ユーザー・権限・写真の件数が一致すること
  ・写真ごとのハッシュ値が一致し、対応するデータがあること
  ・ファイルの最後まで揃っていること（途中で切れていないこと）
  ・ファイル全体のチェックサムが一致すること


■ 7. 新しい組織として復元する

  1. 第 6 章の手順でファイルを検証します。
     「検証 OK」のときだけ、次の入力欄が表示されます。
  2. 「復元後の組織名」を確認します。
     初期値は「元の組織名（復元 2026-10-01）」のような名前です。
  3. 「新しい組織として復元し、自分がその組織の Owner になることを
     確認しました（現在の組織は変更されません）」にチェックを入れます。
  4. 「新しい組織として復元」を押します。
  5. 確認の画面「新しい組織として復元しますか？」で「復元する」を押します
     （やめる場合は「やめる」）。
     復元中は「復元中…（件数が多いと数分かかります）」と表示されます。
     完了の表示が出るまでお待ちください。
  6. 完了すると「復元しました: （組織名）」と、復元した行数・
     ユーザーの対応付けの結果が表示されます。
     新しい組織に追加しなかったユーザーがいる場合は、
     その一覧（氏名・メール・元の権限）も表示されます（第 8 章）。
  7. 「復元した組織に切り替える」を押すと、復元した組織のホームが開きます。
     「閉じる」を押すと結果の表示を閉じます。
     後からでも、画面上部の組織名のプルダウンで切り替えられます。

【復元のときに行われること】
  ・サーバーは、新しい組織を作ってバックアップの内容を 1 回の処理で登録し、
    その後にテーブルごとの件数を照合し、整合性チェックを行います。
    整合性チェックでは、在庫数と在庫の動きの記録、引当・ピッキング・梱包・
    出荷・返品の数量、注文 → 出荷 → 返品 → 交換のつながりなどを確認します。
  ・途中で 1 つでも問題が見つかった場合は、復元全体が取り消されます。
    新しい組織も写真も残らず、現在の組織も変わりません。
  ・復元した人が、新しい組織の Owner になります。
  ・現在の組織（元の組織）で変わるのは、監査ログに
    「この組織から復元を実行」が 1 行記録されることだけです。


■ 8. 復元のときのユーザーの扱い

  画面から復元する場合、バックアップに入っているユーザーは
  次のルールで新しい組織に追加されます。

  ・復元した本人は、新しい組織の Owner になります。
  ・あなたが Owner を務めている組織（どの組織でもかまいません）の
    メンバーは、同じアカウントのまま新しい組織に追加されます。
    ロールと倉庫範囲はバックアップの時点のもの、パスワードはいまのままです。
    元の組織で無効にしていたメンバーは、新しい組織でも無効のままです。
  ・それ以外のユーザー（ほかの事業者のアカウントや、このサーバーに
    アカウントのないメールアドレス）は、アカウントを作らず、
    新しい組織にも追加しません。完了の画面に一覧で表示されます。

  一覧に表示された人が必要な場合は、復元した組織に切り替えてから、
  「設定」→「ユーザー・権限」の「メンバーを招待」で招待してください
  （「招待リンクを作成」で作ったリンクを本人に渡します）。

  このルールは、バックアップファイルを使って、ほかの事業者の
  アカウントを自分の組織に加えることができないようにするためのものです。

  ・操作の記録（誰が操作したか）は、元のまま残ります。
    ただし、別のサーバーに復元した場合、そのサーバーにアカウントのない人の
    操作は、監査ログで「（削除されたユーザー）」と表示されます。
  ・別のサーバーでも、そこで Owner のアカウントを持っていれば
    画面から復元できます。その場合、ほとんどのユーザーは一覧に表示され、
    招待し直しが必要です。
    サーバーごと失った場合の障害復旧は、サーバー運用者による
    コマンドラインでの復元（S3・S6）が適しています。


■ 9. 復元した後に確認すること

  1. 「復元した組織に切り替える」で、復元した組織を開きます。
  2. 代表的な注文をいくつか開き、明細・出荷・返品が元どおりか確認します。
  3. メニュー「在庫・商品」で、在庫数を確認します。
  4. 返品の詳細画面で、検品写真が表示されることを確認します。
  5. メニュー「監査ログ」で記録を確認します。元の記録に加えて
     「バックアップから復元」が 1 行記録されています。
  6. 第 8 章の一覧に表示された人のうち、必要な人を招待します。

【覚えておくこと】
  ・復元の直後は、復元した組織の画面の表示が一時的に遅いことがあります。
    データベースの統計情報の更新が自動で行われると解消します。
  ・注文番号・返品番号などの採番は、バックアップの時点の続きから始まります。
  ・元の組織と復元した組織は別々の組織です。在庫や注文は連動しません。
    どちらの組織で業務を続けるかを決めて、メンバーに周知してください
    （メンバーには組織の切り替えをお願いします）。
    使わなくなった組織のメンバーは、「設定」→「ユーザー・権限」の
    「無効化」でアクセスを止められます。
  ・復元した組織の名前は、「設定」→「組織・運用設定」の「組織名」で
    変更できます。
  ・復元した組織は、画面から削除できません。練習のための復元は控え、
    ファイルの確認には「ファイルを検証」を使ってください。


■ 10. 画面から復元できるファイルの大きさ

  画面から検証・復元できるのは、次の両方を満たすファイルです。
  ・ファイルの大きさ（圧縮された状態）: 既定で 256MB まで
    （サーバーの設定 BACKUP_MAX_UPLOAD_MB）
  ・展開後（圧縮を解いた状態）の大きさ: 既定で 1024MB まで
    （サーバーの設定 BACKUP_MAX_EXPANDED_MB）
  どちらも、サーバー運用者が変更できます。
  いまの上限は、「バックアップから復元」の「バックアップファイル」の欄の説明に
  「画面で扱えるのはファイル 256MB・展開後 1024MB までで、…」のように
  表示されます。

  超えている場合は、次のように表示されます。
  ・「ファイルサイズが上限を超えています」
  ・「展開後のサイズが上限を超えています（大きなバックアップは
    コマンドラインで復元してください）」

  ファイルの大きさが上限より小さくても、展開後の大きさが上限を超えることが
  あります。超えるファイルは、サーバー運用者にコマンドラインでの復元（S3）を
  依頼してください。ファイルは安全な方法で受け渡してください。
  注文の多い組織ほどファイルは大きくなります（目安は第 13 章）。
  画面からのダウンロード（バックアップの取得）には、大きさの上限はありません。


■ 11. 実行履歴と監査ログ

【実行履歴】
  「バックアップ・復元」画面の下の「実行履歴」に、最新 50 件が表示されます。
  項目: 日時・種類（ダウンロード / 復元）・状態（実行中 / 成功 / 失敗）・
  ファイル（ファイル名と SHA-256 の先頭部分）・件数・実行者
  ・コマンドラインで作成したバックアップは、実行者が「コマンドライン」と
    表示されます。
  ・復元の記録は、復元してできた新しい組織の実行履歴に表示されます。
  ・「成功」は、サーバー側でファイルを作り終えたことを示します。
    手元のファイルが完全かどうかは「ファイルを検証」で確認してください。
  ・実行履歴の SHA-256 と、検証結果の SHA-256 を見比べると、
    どの回に作ったファイルかを確認できます。この値はファイルの中身から
    計算したもので、ファイルそのものを外部のツールで計算した値とは
    一致しません。

【監査ログ】
  メニュー「監査ログ」（Owner / Operations Manager）に、次の操作が記録されます。
  「操作の種類」で「バックアップ」を選ぶと、これらだけを表示できます。
  ・「バックアップをダウンロード」
    画面でダウンロードしたとき（その組織に記録）。
    コマンドラインで作成したときは、内容が「コマンドラインでバックアップを
    作成」、実行者が「システム」になります。
  ・「バックアップから復元」
    復元してできた新しい組織に記録されます。
  ・「この組織から復元を実行」
    画面から復元したとき、元の組織に記録されます。
  失敗して取り消された復元は、実行履歴にも監査ログにも残りません。


■ 12. 復元できないときの主なメッセージ

  ・「…チェックサムが一致しません（改ざん・破損の可能性）」
    ファイルが壊れているか、中身が編集されています。
    別の日のバックアップを使ってください。
  ・「最終行（trailer）がありません。ダウンロードが途中で止まった
    ファイルの可能性があります」
    「ファイルを最後まで読めませんでした（破損または途中までのファイル）…」
    ダウンロードが途中で止まったファイルです。取り直すか、
    別の日のバックアップを使ってください。
  ・「データベースの版が異なります（ファイル: … / このシステム: …）。
    同じ版のシステムで復元してください」
    別の版の CommerceOps で作ったファイルです。同じ版のシステムで
    復元してから、システムを更新します。サーバー運用者に相談してください。
  ・「ZIP ファイルは受け付けません。…」
    ZIP に圧縮し直したファイルです。元の .ndjson.gz ファイルを使ってください。
  ・「CommerceOps のバックアップファイル（gzip 圧縮）ではありません」
    「CommerceOps のバックアップファイルではありません」
    別のファイルを選んでいます。
  ・「ファイルサイズが上限を超えています」
    「展開後のサイズが上限を超えています…」
    第 10 章を参照してください。
  ・「復元後の件数が一致しません…。復元を取り消しました」
    「復元後の整合性チェックに失敗したため、復元を取り消しました」
    自動で取り消し済みで、何も変わっていません。開発元へご連絡ください。


■ 13. ファイルの大きさと所要時間の目安（参考値）

  開発元の検証環境で、バックアップファイルを作成した例です
  （2026 年 9 月の計測。写真を含まない条件で、ダウンロードの通信時間は
  含みません）。
  ・注文 約 10 万件（102,500 件）の組織
    ファイルの大きさ 約 250MB（gzip 圧縮後）、作成に 約 3 分 20 秒
  ・注文 約 51 万件（512,505 件）の組織
    ファイルの大きさ 約 1,250MB（gzip 圧縮後）、作成に 約 17 分

  注文 約 10 万件の組織で、画面から扱えるファイルの大きさ（既定 256MB）に
  近い大きさになります。これより大きな組織では、復元はサーバー運用者による
  コマンドライン（S3）で行う前提にしてください。

  これは一例であり、処理時間やファイルの大きさを保証するものでは
  ありません。サーバーの性能、データの量、写真の枚数、通信の速さに
  よって変わります。


■ 14. 障害に備えて Owner が決めておくこと

  ・誰が、いつ、どこにバックアップを保管するか（第 5 章）
  ・サーバーごと使えなくなったときに、どれくらいの時間で復旧したいか、
    どこまでのデータの損失なら許容できるか
  ・サーバー運用者の連絡先と、障害復旧の手順（S6）を事前に確認しておくこと
    （年 1 回以上、検証用の環境で試すことをおすすめします）


──────────────────────────────────────
【サーバー運用者向け】コマンドラインでの操作
──────────────────────────────────────

ここからは、サーバーにログインしてコマンドを実行できる方
（サーバー運用者）向けの内容です。Owner の方は読み飛ばしてかまいません。


■ S1. 前提

【実行できる人】
  本番サーバーのシェルに入れる人だけが使う前提のコマンドです。
  バックアップファイルには個人情報が含まれるため、取り扱いに
  注意してください。

【実行する場所と形】
  コマンドは、アプリが動いているサーバー（またはコンテナ）で、
  環境に合わせて次のどれかの形で実行します。
  ・ビルド済みの環境（Node.js で直接動かす本番など。docs/DEPLOY.md の方法 C）
    server フォルダで次のように実行します。
      node dist/scripts/<名前>-cli.js <オプション>
  ・Docker Compose の環境（docs/DEPLOY.md の方法 A）
    アプリのコンテナの中で実行します。
      docker compose exec app node dist/scripts/<名前>-cli.js <オプション>
  ・開発環境（ソースから動かしている場合）
    CommerceOps のフォルダ（いちばん上の package.json があるフォルダ）で
    次のように実行します。
      npm run <名前> -w server -- <オプション>
  <名前> は backup / restore / integrity / password-reset のいずれかです。
  この章の例は、主にビルド済みの環境の形で書いています。
  相対パスは server フォルダ（Docker ではコンテナの中の /app/server）が
  起点になります。ファイルの場所は絶対パスで指定すると確実です。
  この資料のコマンド例で行末にある「\」は、1 つのコマンドを複数行に
  分けて書くための記号です（bash など）。1 行にまとめて入力しても
  かまいません。
  サーバーの用意・デプロイの構成は docs/DEPLOY.md、日々の運用は
  docs/OPERATIONS.md も参照してください。

【環境変数】
  コマンドは .env ファイルを自動では読みません。アプリと同じ値を
  環境変数として渡したうえで実行します。
  ・DATABASE_URL: データベースの接続先（必須）
  ・DATABASE_SSL: SSL で接続する場合に true
  ・DATA_DIR: 写真の保存先（アプリと同じ場所。未設定のときは ./data）
  ・APP_BASE_URL: パスワード再設定リンクの URL に使用（本番の URL）
  例（ビルド済みの環境）:
    DATABASE_URL=<接続先> DATA_DIR=/var/lib/commerceops \
      node dist/scripts/integrity-cli.js --all
  systemd の EnvironmentFile などでアプリに渡している値と同じものを
  使ってください。
  Docker Compose の環境で docker compose exec を使う場合は、コンテナに
  設定済みの環境変数（DATABASE_URL、DATA_DIR=/data など）がそのまま
  使われます。

【DATA_DIR（写真の保存先）について】
  DATA_DIR は、必ずアプリと同じ場所を指定してください。
  違う場所を指定すると、写真のファイルが見つかりません。
  ・バックアップ（S2）では、見つからなかった写真の件数を警告として表示し、
    終了コード 1 で終わります。ファイルは作成されますが、その写真の画像は
    入りません。DATA_DIR を確認して取り直してください。
  ・そのファイルを検証すると（画面・S3）、欠落した写真の件数が表示されます。
  ・復元（S3）では、写真は DATA_DIR に書き込まれます。

【画面から扱える大きさの設定】
  画面から検証・復元できる大きさは、アプリの環境変数
  BACKUP_MAX_UPLOAD_MB（ファイル。既定 256）と
  BACKUP_MAX_EXPANDED_MB（展開後。既定 1024）で変更できます（単位は MB）。
  上限を上げる場合は、前段のリバースプロキシのアップロード上限と
  タイムアウトも合わせて見直してください。

【環境全体のバックアップ】
  組織ごとのバックアップとは別に、サーバー全体の障害に備えて
  次を行ってください。
  ・PostgreSQL: マネージド DB の自動バックアップ / ポイントインタイム
    リカバリを有効にします。自前で運用する場合は、pg_dump -Fc による
    毎日のバックアップと WAL アーカイブを行います。
  ・写真: DATA_DIR/attachments/ を、ストレージのスナップショットや
    別の場所への同期で保護します。
  データベース全体を過去の状態に戻すと、同じデータベースを使う
  すべての組織が戻ります。1 つの組織だけを戻す場合は、組織ごとの
  バックアップを新しい組織として復元します。


■ S2. バックアップ（backup-cli / npm run backup）

  組織 ID の一覧を表示します。
    node dist/scripts/backup-cli.js --list
  表示の例（組織 ID と組織名。サンプル組織には [sample] が付きます）:
    01920000-0000-7000-8000-000000000001  サンプル雑貨店
    01920000-0000-7000-8000-000000000002  [sample] Sample Commerce

  バックアップを作成します。
    node dist/scripts/backup-cli.js --org <組織ID> \
      --out /secure/backups/shop-a-2026-10-01.ndjson.gz --verify
  開発環境では:
    npm run backup -w server -- --org <組織ID> --out <保存先> --verify

  Docker Compose の環境では、コンテナの中で書き込める /data の下に保存し、
  できたファイルをコンテナの外へコピーして保管します。
    docker compose exec app node dist/scripts/backup-cli.js --org <組織ID> \
      --out /data/backups/shop-a-2026-10-01.ndjson.gz --verify
    docker compose cp app:/data/backups/shop-a-2026-10-01.ndjson.gz ./
  /data は写真と同じ保存領域です。コピーしたファイルは第 5 章のとおり
  保管し、コンテナの中のファイルは不要になったら削除してください。

  オプション
  ・--list: 組織 ID と組織名の一覧を表示します
  ・--org <組織ID>: バックアップする組織（必須）
  ・--out <パス>: 保存先。省略すると
    ./backups/commerceops-backup-<組織IDの先頭8文字>-<日時>.ndjson.gz
  ・--verify: 書き出した後に、ファイル全体を検証します
  ・--allow-missing-files: 写真のファイルが見つからなくても、終了コードを
    1 にしません。DATA_DIR が正しいことを確認したうえで、欠落を承知で
    取る場合だけ使ってください。

  ・画面からダウンロードするファイルと同じ形式です。
    画面から検証・復元することもできます（大きさの上限は第 10 章）。
  ・ファイルは所有者だけが読み書きできる権限（600）で作成されます。
    書き出し中は名前の末尾に .partial が付き、完了すると正式な名前に
    なります。
  ・完了すると、組織・ファイル・大きさ・行数・ユーザー数・写真の数・
    SHA-256・テーブルごとの件数を表示します。--verify を付けた場合は
    「verify: OK」または「verify: NG」と理由を表示します。
  ・写真のファイルが DATA_DIR に見つからなかった場合は、
    「警告: 写真 N 件のファイルが保存先（DATA_DIR=…）に見つかりません。…」
    と表示します。ファイルは作成されますが、その写真の画像は入りません。
  ・次の場合は、終了コード 1 で終わります。
    ・途中で失敗した
    ・--verify で問題が見つかった
    ・写真のファイルが見つからなかった（--allow-missing-files がない場合）
    cron などで毎日実行し、終了コードが 0 以外なら通知する使い方が
    できます。日付入りのファイル名にする例:
      --out /secure/backups/shop-a-$(date +%F).ndjson.gz
  ・画面の「実行履歴」に記録されます（実行者は「コマンドライン」）。
    監査ログには「バックアップをダウンロード」（内容「コマンドラインで
    バックアップを作成」）が記録されます。
  ・業務中に実行しても、作成を始めた時点で揃ったデータになります。


■ S3. 復元（restore-cli / npm run restore）

  検証だけを行います（データベースには接続しません）。
    node dist/scripts/restore-cli.js \
      --file /secure/backups/shop-a-2026-10-01.ndjson.gz --verify-only

  新しい組織として復元します。
    node dist/scripts/restore-cli.js \
      --file /secure/backups/shop-a-2026-10-01.ndjson.gz \
      --actor-email owner@example.com --name "サンプル雑貨店"
  開発環境では:
    npm run restore -w server -- --file <ファイル> --actor-email <メールアドレス>

  Docker Compose の環境では、復元するファイルをコンテナの中の /data の下に
  置いてから実行します。コンテナの中のコマンドは node ユーザーで動くため、
  ファイルはそのユーザーが読める権限にしてください。
    docker compose exec app node dist/scripts/restore-cli.js \
      --file /data/shop-a-2026-10-01.ndjson.gz --actor-email owner@example.com
  復元が終わったら、コンテナの中に置いたファイルは削除してください。

  オプション
  ・--file <パス>: 復元するバックアップファイル（必須）
  ・--verify-only: 検証だけを行います
  ・--actor-email <メールアドレス>: 新しい組織の Owner になるユーザー
    （復元するときは必須）
  ・--actor-name <氏名>: 上のユーザーを新しく作る場合の氏名
    （省略するとメールアドレスの @ より前の部分）
  ・--name <組織名>: 新しい組織の名前
    （省略すると「元の組織名（復元 YYYY-MM-DD）」）

  ・既存の組織・データは変更しません。途中で問題が見つかった場合は
    すべて取り消され、新しい組織も作られません。
  ・画面からの復元とは違い、ファイルの大きさの上限はありません。
  ・バックアップ作成時に見つからなかった写真がある場合は、検証のときに
    「注意: 写真 N 件はバックアップ作成時にファイルが見つからず、画像は
    含まれていません（記録だけ復元されます）」と表示されます。
    検証は OK のままで、復元もできます。
  ・データベースが空でも実行できます（テーブルは自動で作成されます）。
  ・検証・件数の照合・整合性チェックは、画面からの復元と同じく
    復元の処理の中で行います。
  ・--actor-email のユーザーがいない場合は作成し、初期パスワードを
    1 回だけ表示します。ログイン後に変更してもらってください。
    元の Owner のメールアドレスを指定すると、その人が最初にログインして
    確認できます。
  ・バックアップ内のユーザーは、次の順で対応付けます。
    1. 同じユーザー ID のアカウントがあれば、そのアカウント
    2. なければ、同じメールアドレスのアカウント
    3. どちらもなければ、パスワード未設定の「招待中」のアカウントを作成
       （ロールと倉庫範囲はバックアップの時点のもの）
    3 で作られた人がログインするには、パスワード再設定リンクが必要です。
    Owner が「設定」→「ユーザー・権限」の「PWリセット」で発行します。
    ほかの組織にも所属していて Owner が発行できない人は、
    S5 のコマンドで発行します。
  ・完了すると、新しい組織の名前と組織 ID、ユーザーの対応付けの件数
    （existing / matched by email / created (no password)）、
    Owner のメールアドレスを表示します。
  ・念のため、S4 の整合性チェックを --org <新しい組織ID> で実行して
    確認することもできます。
  ・新しい組織の監査ログに「バックアップから復元」が記録され、
    新しい組織の「実行履歴」に復元の記録が表示されます。
  ・組織ごとに新しい組織 ID になります。注文番号などの番号は元のままです。
  ・画面からの復元と同じく、バックアップを作った版と同じデータベースの版の
    システムでだけ復元できます。
  ・復元が終わると（画面からの復元でも同じです）、データベースの統計情報を
    更新する処理（ANALYZE）が自動で予約され、Job worker（アプリと同じ
    プロセス、または別に起動した worker）が実行します。これとは別に、
    15 分ごとの保守処理でも、変更の多いテーブルの統計情報を更新します
    （docs/OPERATIONS.md §8.1）。
    更新されるまでの短い間、復元した組織の画面の表示が遅いことがあります。
    急ぐ場合は、データベースで ANALYZE; を実行してもかまいません
    （業務データは変わりません）。


■ S4. 整合性チェック（integrity-cli / npm run integrity）

    node dist/scripts/integrity-cli.js --all
    node dist/scripts/integrity-cli.js --org <組織ID>
  開発環境では:
    npm run integrity -w server -- --all

  ・読み取りだけを行います。データは変更しません。
  ・在庫数と在庫の動きの記録、引当・ピッキング・梱包・出荷・返品の数量、
    注文 → 出荷 → 返品 → 交換のつながりなどを確認します。
  ・組織ごとに「OK」または「NG」（違反の件数と内容）を表示し、
    違反があれば終了コード 1 で終わります。毎日の定期実行と、
    失敗時の通知をおすすめします。
  ・違反が出た場合は、内容を控え、その組織の最新のバックアップを
    確保してから調査してください。


■ S5. パスワード再設定リンク（password-reset-cli / npm run password-reset）

    node dist/scripts/password-reset-cli.js --email user@example.com
  開発環境では:
    npm run password-reset -w server -- --email user@example.com

  ・パスワード再設定リンク（URL）を表示します。24 時間有効・1 回限りです。
    同じ人の未使用のリンクは無効になります。
  ・リンクの URL には APP_BASE_URL が使われます。本番の URL を設定して
    実行してください（未設定だと http://localhost:5173 のリンクになります）。
    Docker Compose の環境では、.env に設定した APP_BASE_URL が使われます。
  ・アカウントが無効になっているユーザーには発行できません。
  ・本人確認のうえ、安全な方法で本人にだけ渡してください。
    発行したことはセキュリティの記録に残ります。
  ・使う場面: 複数の組織に所属していて Owner が「PWリセット」を
    発行できない人、障害復旧で「招待中」として作られた人など。


■ S6. 空の環境への障害復旧の手順

  サーバーやデータベースを失い、新しい環境に復旧する場合の手順です。

  1. 新しい環境（データベースと DATA_DIR の保存先）を用意し、
     アプリを起動できる状態にします。まだ利用者には公開しません。
  2. データベース全体を戻せる場合（マネージド DB の自動バックアップ・
     ポイントインタイムリカバリ、pg_dump など）は、そちらを優先します。
     写真は、DATA_DIR/attachments/ のコピーを戻します。
  3. データベース全体を戻せない場合は、組織ごとのバックアップファイルを
     S3 の restore-cli で復元します。
     --actor-email には、復元後に最初にログインする Owner
     （元の Owner など）のメールアドレスを指定します。
  4. S4 の整合性チェックを --all で実行し、すべての組織が OK であることを
     確認します。
  5. 画面で、代表的な注文の「注文 → 出荷 → 返品 → 交換」のつながり、
     在庫数、監査ログ、写真の表示を確認します。
     復元の直後は、統計情報が更新されるまで画面の表示が遅いことがあります
     （S3）。
  6. 「招待中」として作られた利用者に、パスワード再設定リンクを渡します
     （Owner が「PWリセット」で発行。発行できない人は S5）。
     そのうえで、DNS や接続先を切り替えて公開します。
     ログイン中のセッションはバックアップに含まれないため、
     全員があらためてログインします。
  7. 障害の内容と、復旧の手順・結果を記録します。

  この手順は、年 1 回以上、検証用の環境で試しておくことをおすすめします。
