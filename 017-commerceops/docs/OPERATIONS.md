# 運用手順 (OPERATIONS.md)

対象: CommerceOps を自社サーバー / PaaS で運用する人（サーバー運用者）と、各組織の Owner。
最終更新: Phase 11（2026-09-30）。サーバーの用意・デプロイ構成（Docker / Render / Node.js 直接）は docs/DEPLOY.md。

---

## 1. 構成

| 要素 | 役割 | 永続化 |
|---|---|---|
| Web/API プロセス（`npm start -w server`） | 画面の配信・API | なし（ステートレス） |
| Job worker（`RUN_WORKER=true` で同一プロセス、または `npm run worker -w server`） | 自動引当ジョブ、保守処理（1 分ごと） | なし |
| PostgreSQL 16 | 全データ（RLS で組織分離） | **要バックアップ** |
| `DATA_DIR`（既定 `./data`） | 返品検品写真（`attachments/`）、アップロードの一時ファイル（`tmp/`、処理後に削除） | **写真は要バックアップ** |

- アプリ用の DB ユーザーは SUPERUSER / BYPASSRLS を持たないこと（持つと RLS が効かず組織分離が崩れる）。
- ヘルスチェック: `GET /healthz`（プロセス）/ `GET /readyz`（DB 接続。503 なら DB に届いていない）。

## 2. 日常の確認

| 頻度 | 内容 | 方法 |
|---|---|---|
| 常時 | 死活 | `/readyz` を監視（PaaS のヘルスチェックに設定） |
| 毎日 | 整合性チェック（在庫台帳・引当・Pick/梱包・出荷・返品・注文→出荷→返品→交換の参照） | `npm run integrity -w server -- --all`（違反があれば終了コード 1。cron / 定期ジョブで実行し、失敗を通知） |
| 毎日 | 組織ごとのバックアップ | §3.1 |
| 毎日 | エラーログ | `unhandled error` / `job failed` を確認。リクエスト ID（画面のエラー表示にも出る）で追跡 |
| 毎週 | 例外キューの滞留、失敗ジョブ | 画面の例外キュー / `SELECT type, count(*) FROM jobs WHERE status = 'dead' GROUP BY 1` |
| リリース前 | 依存ライブラリの脆弱性 | `npm audit --omit=dev`（SECURITY.md §6） |

整合性チェックで違反が出た場合: 内容（どの在庫・どの Fulfillment か）を控え、該当組織の最新バックアップを確保してから調査する。
在庫の数だけが食い違う場合は、在庫調整（理由必須・監査ログに記録）で実数に合わせる。原因が分からない場合は開発元へ連絡する。

## 3. バックアップ

> コマンドラインの実行方法: 開発環境では `npm run <名前> -w server -- ...`（tsx）、ビルド済みの環境（Docker・本番）では
> `node dist/scripts/<名前>-cli.js ...`（`server/` で実行。Docker では `docker compose exec app node dist/scripts/backup-cli.js ...`）。
> `.env` ファイルは自動では読まないので、`DATABASE_URL`・`DATA_DIR` はアプリと同じ値を環境変数で渡す（`DATA_DIR` が違うと写真が「欠落」になり、
> backup-cli は警告して終了コード 1 を返す。欠落を承知で取る場合のみ `--allow-missing-files`）。

### 3.1 組織単位のバックアップ（アプリの機能）
組織のデータを 1 ファイル（gzip 圧縮した NDJSON、`commerceops-backup-YYYYMMDDTHHMMSS.ndjson.gz`）にまとめる。

**含むもの**: 倉庫・ロケーション・商品・バーコード・販売チャネル・Import Profile・顧客・取込履歴・注文と明細・状態/住所の履歴・保留・
在庫（ロケーション別）と在庫の動き・引当と引当実行履歴・Fulfillment・Wave・Pick タスク/記録・梱包/scan 記録・出荷（荷物）と明細・
返品/明細/検品・交換・例外と対応履歴・検品写真（ファイル本体）・監査ログ・採番カウンタ・ユーザー（氏名・メール・状態）と権限。
**含まないもの**: パスワード（ハッシュも含めない）、ログインセッション、招待・再設定リンク、ジョブ、バックアップの実行履歴。

**ファイルの中身**: 1 行目にヘッダー（形式の版・データベースの版 schemaVersion・アプリの版 appVersion・作成日時・組織）、
最終行にトレーラー（テーブル別の件数と SHA-256、全体の SHA-256）。復元時にこれらで欠落・破損・改ざんを検出する。
（チェックサムは破損・途中切れ・うっかりした編集の検出用で、悪意ある作成者の署名ではない。細工したファイルでも他の組織には影響しない — SECURITY.md）

**取得方法**
- 画面: Owner が「設定 → バックアップ・復元 → バックアップをダウンロード」。
- コマンドライン（サーバー運用者、定期実行向け）:
  ```bash
  cd server
  npm run backup -- --list                                  # 組織 ID の一覧
  npm run backup -- --org <組織ID> --out /secure/backups/shop-a-$(date +%F).ndjson.gz --verify
  # ビルド済み環境（本番）では: node dist/scripts/backup-cli.js --org <組織ID> --out <path> --verify
  ```
  ファイルは権限 600 で作成。`--verify` で書き出し後に全件を検証する。
- 一貫性: REPEATABLE READ の読み取り専用トランザクションで取得するため、業務中に実行しても時点の揃ったデータになる。

**保管の注意（必須）**
- **顧客の氏名・住所・電話・メールを含む**。暗号化されたストレージに、アクセスできる人を限定して保管する。メール添付・チャット共有をしない。
- 保管期間を決めて古いものを削除する（例: 日次 14 世代 + 月次 12 世代）。
- ダウンロード・復元は監査ログ（`backup.export` / `backup.restore`）と「実行履歴」に残る。

### 3.2 環境全体のバックアップ（DB・写真）
組織単位のバックアップとは別に、サーバー全体の障害に備えて次を行う。
- PostgreSQL: マネージド DB の自動バックアップ / PITR（ポイントインタイムリカバリ）を有効にする。自前運用なら `pg_dump -Fc` を日次 + WAL アーカイブ。
- 写真: `DATA_DIR/attachments/` をストレージのスナップショット / 別リージョンへの同期で保護する。
- 復旧時間の目安（RTO）と許容できるデータ損失（RPO）を事前に決め、年 1 回以上、§4.3 の手順を検証環境で試す。

## 4. 復元

### 4.1 画面から（Owner）— 新しい組織として復元
1. 「設定 → バックアップ・復元」でファイルを選び「ファイルを検証」。形式・件数・チェックサム・データベースの版を確認する（この時点では何も書き込まない）。
2. 検証 OK なら組織名を確認し、「新しい組織として復元」。**現在の組織は変更されない。**
3. サーバーで 1 トランザクションで投入 → 件数照合 → 整合性チェック。問題があれば全体を取り消す（組織も写真も残らない）。
4. 復元した人が新しい組織の Owner になる。「復元した組織に切り替える」で確認する。

ユーザーの扱い: **復元する人が Owner を務める組織のメンバー**だけを、同じアカウントのまま新しい組織に追加する（元の権限で）。
それ以外のユーザー（別の事業者のアカウント・この環境にいないメールアドレス）はアカウントを作らず、完了画面に一覧を出すので、必要なら招待する。

上限: 画面から扱えるのはファイル `BACKUP_MAX_UPLOAD_MB`（既定 256MB）かつ展開後 `BACKUP_MAX_EXPANDED_MB`（既定 1024MB）まで（画面に表示）。
超える場合は §4.2（目安: 約 10 万注文の組織で gzip 約 260MB。TEST_REPORT.md）。上限を上げる場合は、リバースプロキシのアップロード上限・タイムアウトも合わせる。

### 4.2 コマンドライン（サーバー運用者）— 空の環境・大きなファイル
```bash
cd server
# 1) 検証だけ（書き込みなし）
npm run restore -- --file /secure/backups/shop-a.ndjson.gz --verify-only
# 2) 復元（新しい組織として）。--actor-email のユーザーが新しい組織の Owner になる
npm run restore -- --file /secure/backups/shop-a.ndjson.gz --actor-email owner@example.com [--name "組織名"]
# ビルド済み環境では: node dist/scripts/restore-cli.js --file <path> --actor-email <メール>
```
- DB が空でもよい（マイグレーションを自動適用する）。`DATABASE_URL` と `DATA_DIR`（写真の保存先）を本番と同じに設定して実行する。
- `--actor-email` のユーザーが存在しなければ作成し、初期パスワードを 1 回だけ表示する。
- バックアップ内のユーザーは、ID → メールアドレスの順に既存アカウントへ対応付け、無ければ**パスワード未設定の「招待中」**として作成する。
  ログインできるようにするには、Owner が「設定 → ユーザー・権限」でパスワード再設定リンクを発行して本人に渡す。
- 完了時に件数と整合性を確認済み。念のため `npm run integrity -- --org <新しい組織ID>` でも確認できる。

### 4.3 障害復旧（DR）の手順
1. 新しい環境（DB・`DATA_DIR`）を用意し、アプリを起動できる状態にする（まだ利用者には公開しない）。
2. DB 全体を復旧できる場合（PITR / `pg_dump`）はそれを優先する（全組織・ユーザー・セッション以外すべて戻る）。写真は §3.2 のコピーを `DATA_DIR/attachments/` に戻す。
3. DB 全体を戻せない場合は、組織ごとのバックアップを §4.2 の CLI で復元する（組織ごとに新しい組織 ID になる）。
4. `npm run integrity -- --all` が全組織 OK であることを確認する。
5. 代表的な注文で「注文 → 出荷 → 返品 → 交換」がつながっていること、在庫数、監査ログ、写真の表示を画面で確認する。
6. 利用者のパスワード再設定リンクを発行（§4.2 で作成されたユーザー）し、DNS / 接続先を切り替えて公開する。
7. 障害の内容と復旧手順の結果を記録する。

### 4.4 復元できないとき（主なエラー）
| 表示 | 意味 | 対処 |
|---|---|---|
| チェックサムが一致しません | ファイルの破損・編集 | 別の世代のバックアップを使う |
| trailer がありません / 最後まで読めませんでした | ダウンロードが途中で止まった | 取り直す・別の世代を使う |
| データベースの版が異なります | 別の版の CommerceOps で作成 | 同じ版のシステムで復元してから更新する（§7） |
| ZIP ファイルは受け付けません | .zip に圧縮し直した | 元の `.ndjson.gz` を使う |
| 復元後の件数が一致しません / 整合性チェックに失敗 | 中身の矛盾 | 自動で取り消し済み（何も変わっていない）。開発元へ連絡 |
| ファイルサイズが上限を超えています | 画面の上限超過 | §4.2 の CLI を使う |

## 5. アカウントの運用
- パスワードを忘れた: Owner が「設定 → ユーザー・権限」から再設定リンクを発行（24 時間・1 回限り）。
- 複数の組織に所属していて Owner から発行できない（`USER_IN_OTHER_ORGANIZATION`）: サーバー運用者が本人確認のうえ
  `npm run password-reset -w server -- --email user@example.com` でリンクを発行する（セキュリティイベントに記録）。
- ログイン 5 回失敗で 15 分ロック（自動解除）。
- 退職者: 「ユーザー・権限」で無効化（その組織へのアクセスを止める。監査ログの記録は残る）。

## 6. ログ
- 形式: JSON（pino）。リクエスト ID・メソッド・パス（クエリ文字列なし）・状態・所要時間。
- 出さないもの: Cookie・CSRF トークン・Authorization、リクエスト/レスポンス本文、検索語、DB エラーの行データ（PostgreSQL の detail）。
- 監査ログ（DB、画面「監査ログ」）: 重要操作の「誰が・いつ・何を」。追記専用で変更・削除できない。個人情報は記録しない。
- セキュリティイベント（DB）: ログイン成功/失敗・ロック・パスワード変更/再設定・招待の承諾。メールアドレスはハッシュで記録。

## 7. アップデート
1. 全組織のバックアップ（§3.1 CLI）と DB 全体のバックアップ（§3.2）を取る。
2. 新しい版をデプロイし、`npm run db:migrate -w server`（起動時にも自動適用）。
3. `npm run integrity -w server -- --all` で確認。
- バックアップファイルは作成した版の schemaVersion でのみ復元できる。古いバックアップを新しい版へ戻す場合は、
  同じ版の環境で復元 → アップデートの順に行う（版違いのファイルは検証で拒否される）。

## 8. データの保持期限（自動）
| データ | 期限 | 処理 |
|---|---|---|
| 取込プレビュー | 24 時間 | 期限切れにする |
| 取込ステージングの正規化データ（個人情報を含む） | 確定/取消/期限切れから 7 日 | 削除（件数・判定結果は残す） |
| ログインセッション | アイドル 12 時間 / 最長 7 日 | 失効・削除 |
| Pick タスクの担当（claim） | 設定の期限（既定 30 分）操作なし | 自動で解除（監査ログに記録） |
| 完了した Job | 7 日（打ち切られた Job は 30 日） | 削除 |
| セキュリティイベント | 365 日 | 削除 |
| 使用済み・期限切れの再設定トークン | 30 日 | 削除 |
| 注文・出荷・返品・在庫の動き・監査ログ | 期限なし（削除しない） | 保管期間の要件がある場合は購入者の方針で運用 |

保守処理は Job worker が 1 分ごとに実行する（保持期限の削除は 1 時間ごと）。

### 8.1 統計情報の更新（自動）
- 15 分ごとに、前回から 500 行以上変わった業務テーブルを `ANALYZE` する（`db.analyzeChangedTables`）。組織の復元の直後と、100 件以上の注文 CSV 取込の直後にも実行する。
- 理由: 組織が少ない DB では、後から作った組織（や復元した組織）の行数が次の ANALYZE まで「1 行」と見積もられ、画面の問い合わせが
  遅くなることがある（負荷検証で、大きな組織がある DB に作った 500 注文の組織の注文詳細が 6ms → 293ms。TEST_REPORT.md）。
- 大量の取込・復元の直後に遅いと感じた場合は、DB で `ANALYZE;` を実行してよい（業務データは変わらない）。
- 整合性チェック（`npm run integrity`）は統計情報に関係なくハッシュ結合で実行する（作成直後の組織でも数十 ms〜）。

## 9. 障害対応の早見表
| 症状 | 確認 | 対処 |
|---|---|---|
| 画面が開かない | `/healthz` | プロセス再起動、ログ確認 |
| 「サーバーに接続できません」が多発 | `/readyz` が 503 | DB の稼働・接続数（`DATABASE_POOL_MAX`）・ネットワーク |
| 「他の操作と競合しました」 | 同じ注文・作業を同時に操作 | 画面を再読み込みしてやり直す（二重処理にはならない） |
| 作ったばかりの組織・復元した組織の画面だけ遅い | 統計情報（§8.1） | 15 分以内に自動で解消。急ぐ場合は DB で `ANALYZE;` |
| 自動引当が進まない | `jobs` の queued / dead | worker が動いているか（`RUN_WORKER`）、dead の `last_error` |
| 在庫が合わない | `npm run integrity` | §2 の手順 |
| 写真が表示されない | `DATA_DIR/attachments` | 永続ディスクがマウントされているか |
| 429（リクエストが多すぎます） | `RATE_LIMIT_MAX` / `TRUST_PROXY` | プロキシ背後で `TRUST_PROXY=true` になっているか（全員が同じ IP 扱いになる） |
