# 設計判断ログ (DECISIONS.md)

形式: ADR-番号 / 日付 / 決定 / 理由 / 代替案。日付はすべて実装時点（2026-09-30〜）。

## ADR-001 専用フォルダで独立開発
- 決定: リポジトリ直下 `017-commerceops/` に閉じたモノレポ（npm workspaces: server, web, e2e, load）。他商品のコードは参照・変更しない。
- 理由: 指示「既存#001〜#016や他プロジェクトを変更せず専用フォルダで開始」。

## ADR-002 技術スタック
- 決定: Node.js 22 LTS / TypeScript 6.0 / Fastify 5 / PostgreSQL 16 / pg 8 / zod 4 / React 19 / Vite 7 / React Router 7 / TanStack Query 5 / vite-plugin-pwa 1.3 / Vitest 4 / Playwright 1.56。
- 理由: 実装時点（2026-09）で「安定構成」を優先。最新メジャーの Vite 8・Vitest 5・TypeScript 7・React Router 8 はリリースから日が浅いため採用せず、
  1 つ前の成熟ラインを選択（Vite 7.3 / Vitest 4.1 / TS 6.0 / RR 7.18）。Playwright は実行環境にプリインストールされた Chromium 141 (rev 1194) と一致する 1.56.1 に固定。
- 代替案: Next.js（SSR 不要・PWA/オフライン制御を単純にしたいので不採用）、NestJS（規模に対し重い）。

## ADR-003 ORM を使わず手書き SQL
- 決定: `pg` + parameterized SQL。マイグレーションは番号付き SQL ファイル。
- 理由: 引当・出荷確定・claim は「条件付き UPDATE」「FOR UPDATE」「SKIP LOCKED」「advisory lock」など DB 機能を明示的に使う必要があり、
  500 万注文規模のインデックス設計も SQL で直接管理したい。SQL インジェクションは全クエリの placeholder 化で防ぐ（文字列連結禁止、lint ルール + レビュー）。

## ADR-004 マルチテナント = 共有スキーマ + RLS(FORCE) + 複合キー
- 決定: 全業務テーブルに `organization_id`、PK は `(organization_id, id)`、FK も `(organization_id, xxx_id)` の複合。
  RLS を ENABLE + FORCE し、ポリシー `organization_id = app_org_id()`（`current_setting('app.org_id')`）。リクエストごとに `SET LOCAL` 相当を設定。
- 理由: アプリの WHERE 漏れがあっても他テナント行は見えない（多層防御）。FK は RLS をバイパスするため、複合 FK で「他テナントの親を参照する子行」を DB 制約で禁止。
  さらに複合 PK のため、別組織としての復元時に UUID を振り直す必要がない（ADR-012）。
- 代替案: テナントごとスキーマ/DB（運用コスト増・マイグレーションが煩雑）。

## ADR-005 ID は UUIDv7（アプリ生成）+ 人が読む連番
- 決定: 主キーは UUIDv7（時系列順で B-tree 局所性が良い）。画面表示は組織内連番（SO-/F-/W-/SH-/RT-/EX-/EXC-）。
- 連番はカウンタ行をブロック単位で払い出す（別コネクションで即コミット、欠番は許容）ことで長時間ロックを避ける。

## ADR-006 認証はサーバーセッション
- 決定: 32 バイト乱数トークンを HttpOnly Cookie に、DB には SHA-256 のみ保存。アイドル 12 時間 / 絶対 7 日（設定可）。
  CSRF は同期トークン（セッションに保存し `X-CSRF-Token` ヘッダで照合）+ SameSite=Lax。パスワードは scrypt（N=2^15, r=8, p=3 = OWASP の N=2^17,p=1 と同等強度）。
- 理由: 倉庫の共有 iPad/スマホで即時ログアウト・無効化ができる。外部 IdP 依存なし（有料契約不要）。
- 代替案: Auth0/Clerk 等（有料・外部依存）、JWT（失効が難しい）。

## ADR-007 Job キューは PostgreSQL
- 決定: `jobs` テーブル + `FOR UPDATE SKIP LOCKED`、`dedupe_key`（queued/running 中は UNIQUE）、リトライ回数、指数バックオフ。
- 理由: Redis 等の追加インフラ・費用が不要。引当 Job は dedupe で組織ごとに同時 1 本、さらに注文行ロック + 残必要数再計算で冪等。

## ADR-008 在庫はロケーション単位で引当
- 決定: `inventory_balances` は (location, product) 単位。Available = on_hand − allocated − held。引当はロケーションまで確定させ、Pick 行はそこから生成。
- 理由: Pick List のロケーションが引当時に確定し、Short Pick 時の在庫調査対象（どの棚か）が明確。ロケーションを使わない倉庫は DEFAULT ロケーション 1 つで運用可能。

## ADR-009 Short Pick は on_hand を減らさず held へ
- 決定: 現物なし等の数量は `held` に移し Available から除外、例外キューで「紛失確定/発見」を人が決める。
- 理由: 「在庫を勝手に調整しない」と「同じ幻の在庫に再引当しない」を両立。

## ADR-010 注文状態は導出 + 許可遷移の検証
- 決定: 状態は事実から導出し、許可遷移表で検証してから保存・履歴化（FULFILLMENT_RULES.md）。
- 理由: 複数 Fulfillment/分割出荷/返品が絡むと手動遷移は不整合を生みやすい。導出にすることで常に事実と一致し、遷移表でバグを検知できる。

## ADR-011 交換は Replacement Order + Replacement Fulfillment
- 決定: 交換品は `order_type='replacement'` の注文として作成し、通常の引当→Fulfillment(type=replacement)→Wave→Pick→Pack→Ship を通す。
- 理由: 「交換は通常の Allocation→Pick→Pack→Ship を通す」要件を、特別経路を作らずに満たす。元注文の状態導出を汚さない。KPI では replacement を受注件数から除外。

## ADR-012 バックアップは組織単位の gzip NDJSON（ZIP を受け付けない）
- 決定: `commerceops-backup-*.ndjson.gz`（ヘッダ行: schemaVersion/appVersion/日時/組織、行データ、トレーラ行: テーブル別件数と SHA-256、全体 SHA-256）。
  復元は検証（チェックサム・件数・スキーマ版・参照整合）→ 新しい組織として 1 トランザクションで投入 → 復元後の整合性検証。失敗時はロールバックで現行データ非破壊。
- 理由: ZIP を扱わないことで Zip Slip / パストラバーサルを構造的に排除。複合 PK のため別組織として復元しても ID 衝突しない（ユーザー ID のみメールで対応付け）。
- 環境全体の DR は PostgreSQL のマネージドバックアップ/PITR または `pg_dump`（OPERATIONS.md）。

## ADR-013 PWA キャッシュ範囲
- 決定: アプリシェル（静的アセット）のみ precache。`/api` はキャッシュしない（個人情報を端末に残さない）。
  オフライン下書きは Pick scan のみ（IndexedDB、未同期表示、再接続時にサーバー再検証）。
- 理由: 要件「Pack 完了、Shipment 確定、在庫減算、Return Restock 等を危険なオフライン確定にしない」。

## ADR-014 バーコード
- 決定: 読取はネイティブ `BarcodeDetector`（Android Chrome 等）優先、非対応（iOS Safari 等）は `@zxing/browser`。生成は `bwip-js`。
  対応済みと表記するのは、採用ライブラリ（ZXing）で自動テストにより実測デコードできたシンボルのみ（TEST_REPORT.md）。
  外部画像認識 API には送らない。カメラ不可時はハンディスキャナ（キーボード入力）/手入力 fallback。

## ADR-015 帳票は印刷用 HTML
- 決定: Pick List / Packing Slip / Shipment 作業票 / Return 受領票 / 注文識別コードは印刷 CSS 付き HTML（ブラウザで紙/PDF）。
  PDF 生成を Playwright の `page.pdf()` で自動テスト。配送会社公式送り状は再現しない。

## ADR-016 CSV Import Profile は宣言的変換のみ
- 決定: 許可リストの変換（trim/nfkc/removeChars/リテラル replace/map 等）のみ。正規表現・式・コード実行は不可。
- 理由: 任意コード実行禁止、ReDoS 防止、プロファイルの説明可能性。

## ADR-017 Picker/Packer の個人情報
- 決定: Pick API は注文番号/Fulfillment 番号以外の注文情報を返さない。Pack API は送付先の氏名・住所のみ（電話/メールなし）。
- 理由: 最小権限（「Pickerへ不要な住所全文を出さない」）。

## ADR-018 ロック順序と deadlock 時の自動再試行
- 決定: 作業系（Pick/Pack/出荷）は Fulfillment → 作業行（PickTask / PackSession / Shipment）→（状態再計算で）Order の順にロックする。
  注文キャンセル・保留は Order → Fulfillment の順（業務上まれな競合）。PostgreSQL が検出した deadlock（40P01）とシリアライズ失敗（40001）は
  `withTenant` がトランザクション全体を最大 2〜3 回再試行する。冪等キー（client_event_id / requestId / movement idempotency_key）により再試行でも二重処理しない。
- 理由: すべての経路で完全に同じ順序にするより、頻出経路の順序統一 + 検出・再試行 + 冪等化の方が単純で安全。

## ADR-019 追跡番号の正規化と一意性
- 決定: 追跡番号は NFKC → 空白/ハイフン除去 → 英大文字 → `^[A-Z0-9]{4,40}$` で保存。一意性は (組織, 配送会社, 追跡番号)、取消済みを除く（部分 UNIQUE）。
- 理由: 送り状の印字（ハイフン区切り）とバーコード読取値（区切りなし）を同一視して重複・検索漏れを防ぐ。配送会社が違えば同じ番号体系があり得る。

## ADR-020 KPI の定義と個人評価をしない方針
- 決定: KPI は物流オペレーションの指標のみ。率は必ず分子・分母・定義文を API と画面で返す/表示する。期間は組織タイムゾーンの日付。
  受注件数などから交換品の注文（order_type=replacement）を除外。作業者ごとの指標・ランキングは作らない（作業割当画面の「現在の担当数」は進行中の件数のみ）。
- 理由: 要件「率は分母/期間を明示し個人評価を自動化しない」。

## ADR-021 CSV 出力と個人情報
- 決定: CSV 出力は `export.csv` + 対象データの閲覧権限が必要。注文の個人情報は要求レベル（none / ship_to / full）と本人の権限の小さい方まで。
  すべてのセルに数式インジェクション対策、UTF-8(BOM) / Shift_JIS、最大 10 万行。出力は監査ログに件数・範囲・個人情報レベルのみ記録（中身は記録しない）。
  ファイル名は ASCII（`orders_YYYY-MM-DD.csv` 等）。環境によって非 ASCII のダウンロード名が「download」になるため。

## ADR-022 復元時のユーザー対応付け（画面は Owner の管理範囲のみ、CLI は運用者として全件）
- 決定: 画面からの復元（`userPolicy: owner-scoped`）では、バックアップ内のユーザーのうち「復元する人が Owner を務める組織のメンバー（と本人）」だけを
  同じアカウントのまま新しい組織へ追加する。それ以外はアカウントを作らず、メンバーにもせず、完了画面で一覧を返す（Owner が必要なら招待）。
  サーバー運用者の CLI（`userPolicy: trusted`）は ID → メールアドレス → 作成（パスワード未設定の「招待中」）の順に対応付ける（空の環境への障害復旧）。
  履歴行のユーザー ID 列（USER_COLUMNS）は対応付けに合わせて付け替える。対応付けないユーザーの ID は履歴の記録としてそのまま残す（外部キーなし）。
- 理由: バックアップファイルは誰でも作れる（チェックサムは改ざん検知であって署名ではない）。細工したファイルで他の事業者のアカウントを自分の組織に
  加えたり、メールアドレスを先取りしたりできないようにする。障害復旧は運用者の操作なので全件復元が必要。

## ADR-023 アカウントにパスワードを設定できる経路を限定する
- 決定: (1) 招待の承諾: 有効なアカウントは本人のパスワードが必要（未設定なら常に不一致）。無効化されたアカウントは拒否。
  パスワード未設定のアカウントが他の組織に所属していたら拒否（`ACCOUNT_NEEDS_RESET`）。(2) Owner による再設定リンク発行: 対象ユーザーが所属する
  すべての組織で自分が Owner の場合のみ。(1)(2) とも無効化中の所属も「所属」に数える（後で有効に戻されると同じ問題になるため）（`USER_IN_OTHER_ORGANIZATION`）。それ以外はサーバー運用者が CLI（`password-reset`）で本人確認のうえ発行。
- 理由: 招待・再設定リンクは発行した本人も開ける（メール送信をせず、Owner が本人に渡す運用のため）。組織をまたいで所属するアカウントのパスワードを
  一方の組織の Owner が設定できると、もう一方の組織のデータにアクセスできてしまう。

## ADR-024 バックアップのアップロードは一時ファイルへストリーミング
- 決定: 検証・復元のアップロードはメモリに載せず `DATA_DIR/tmp` にサーバー生成名で書き出し（権限 600）、gzip の先頭バイトで ZIP/非 gzip を拒否、
  処理後に必ず削除。上限は通常のアップロード（`MAX_UPLOAD_MB`、20MB）と分けて `BACKUP_MAX_UPLOAD_MB`（既定 1024MB）。展開後 1GB を超える場合は CLI。
  上限超過は 413 `FILE_TOO_LARGE`。
- 理由: 1 年分の注文を持つ組織のバックアップは数十〜数百 MB になり得る。小さなサーバーでもメモリを使い切らずに扱う。

## ADR-025 運用データの保持期限
- 決定: 保守処理で、完了した Job（7 日、打ち切りは 30 日）、セキュリティイベント（365 日）、使用済み・期限切れの再設定トークン（30 日）を削除する。
  業務データ・監査ログは削除しない。期限は OPERATIONS.md §8。
- 理由: 保守 Job は毎分 1 行生まれ、放置すると年 50 万行規模で DB 容量（運用費）を圧迫する。業務・監査の記録は購入者の保管方針に委ねる。

## ADR-026 RLS（FORCE）の下での検索設計: LEAKPROOF な演算子だけを索引条件にする
- 決定: 部分一致・前方一致の検索は「LIKE / ILIKE / pg_trgm の類似演算子」ではなく、LEAKPROOF な演算子で索引を使う形にする。
  前方一致 = `starts_with`（`^@`）+ `text_pattern_ops` の B-tree、完全一致 = `=`（texteq は LEAKPROOF）、複数値 = `= ANY(...)`。
  氏名の「含む」検索は新しい順の上位 1 万件に限定して ILIKE で絞る（全件走査しない）。トライグラム索引は削除（0002_scale_indexes.sql）。
  横断検索・注文一覧の検索は「番号の完全一致」「外部注文番号の前方一致」「SKU」「氏名の前方一致」などの分岐を UNION し、`MATERIALIZED` の CTE で
  ヒットした ID を先に確定してからページを切る。
- 理由: 実測（段階 A: 10 万注文）で、FORCE RLS のテーブルでは LEAKPROOF でない演算子が行レベルセキュリティの条件より先に評価できないため
  索引条件に使われず、トライグラム索引が一切使われない（外部注文番号の前方一致 3.0 秒）ことを確認した。変更後は 51 万注文で 155ms。
- 影響: 氏名の「含む」検索は直近 1 万件の範囲になる（画面に明記）。前方一致・完全一致は全期間。

## ADR-027 一覧の件数は上限付きで数える
- 決定: 一覧 API の総件数は `count(*)` を 10,001 件で打ち切り（`cappedCount`）、超えたら `totalCapped: true` を返す。
  画面は「10,000件以上（条件で絞り込んでください）」と表示し、ページ送りはそのまま使える。ページの行は「ページ分の ID を先に取る CTE → 詳細を JOIN」で取得。
- 理由: 50 万注文規模で全件数の集計が一覧の応答時間の大半を占めた。業務上、1 万件を超える一覧の正確な件数は判断に使わない（絞り込みで扱う）。

## ADR-028 自動引当の候補抽出で「引当できる見込みのない欠品注文」を除く
- 決定: 自動引当（allocation.run）の候補から、未解決の欠品例外がある注文のうち、その注文の未引当 SKU に引当可能在庫（棚の OnHand − 引当 − 調査中 > 0、
  有効な Pick ロケーション・有効な倉庫）が 1 つもない注文を除く。在庫が入った SKU を含む注文は候補に戻る（テスト: 欠品が続く注文が他の注文の引当を妨げない）。
- 理由: 欠品注文が増えると、毎回同じ注文を先頭から試して処理枠（1 回 500 件）を使い切り、在庫のある新しい注文が引当されない状態が起きた（Phase 10 の負荷検証で発見）。

## ADR-029 規模検証の方法（販売保証値ではない）
- 決定: 実 API で「テンプレート組織」（1,025 注文: 取込 → 引当 → Wave → Pick → 梱包 → 出荷 → 返品/交換、進行中・保留・取消・Short を含む）を作り、
  その業務データを SQL で大きな組織へ複製（UUIDv7 の時刻を保って ID を振り直し、番号・外部注文番号・追跡番号・冪等キーも一意に変換、日時を 1 年に分散）、
  在庫残高は在庫移動と引当から再計算。生成後に整合性チェックが通ることを確認してから API・SQL の応答時間・実行計画・容量・バックアップ速度を測る。
  複製には RLS をバイパスするデータ生成専用ロール（commerceops_loadadmin）を使い、アプリ本体は使わない。
  1 日 50 / 500 / 5,000 注文の業務フローは複製せず、実 API（Picker 4 人・Packer 4 人が並行）で流して測る。同時実行の検証は load/contention.ts。
- 理由: 仕様の目安（Order 500 万等）の規模をこの検証環境のディスク（約 38GB）で作ることはできない（51 万注文で DB 12GB）。
  実測した規模・環境の値だけを TEST_REPORT.md に記録し、対応件数として広告しない。

## ADR-030 UPC-A と先頭 0 の EAN-13 を同じ商品コードとして照合する
- 決定: 商品コードの照合（Pick / 梱包 / 商品確認 / 検索 / 一覧）で、12 桁の UPC-A と「0 + UPC-A」の 13 桁 EAN-13 を同じ GTIN として扱う
  （チェックディジットが正しい場合のみ）。同じ GTIN の別表記を別の商品に登録することはできない。スマホのオフライン判定も同じ規則。
- 理由: 同じバーコードでも読取ライブラリによって 12 桁・13 桁のどちらでも返る（ZXing は先頭 0 の EAN-13 を UPC-A の 12 桁で返すことを自動テストで確認）。
  完全一致だけだと、正しい商品を読んでも「違う商品」と拒否される。

## ADR-031 Service Worker はアプリ起動時に 1 回だけ登録する
- 決定: `PwaProvider`（アプリの最上位）で登録し、更新の案内は各画面の枠（Layout / MobileShell）が表示する。ログイン画面でも登録される。
- 理由: 画面の枠の中でだけ登録していたため、ログイン前の画面では Service Worker が無く、ホーム画面への追加・アプリの殻のキャッシュが初回ログイン後まで遅れた
  （端末別 E2E で発見）。

## ADR-032 状態の更新は FOR NO KEY UPDATE、複数行のロックは ID 順
- 決定: Fulfillment・Wave・注文の状態を再計算して更新する処理は、対象行を `FOR NO KEY UPDATE` でロックする（キー列は変えないため）。
  Pick で複数の Fulfillment 明細・Fulfillment・注文を更新するときは、それぞれ ID 順にロックする。
  同じ冪等キー（clientEventId）の再送が同時に届いた場合は、タスクの行ロックを取ってから冪等チェックをやり直し、先の結果を返す。
- 理由: 子行（pick_events 等）の INSERT は外部キー検査で親行に KEY SHARE ロックを取る。2 つの取引が同じ親行に KEY SHARE を持ったまま
  `FOR UPDATE` を求めると互いに待ってデッドロックする（競合検証: 同じ注文を含む 2 タスクの同時 Pick で再試行切れ 409、Pick 工程 117 秒）。
  `FOR NO KEY UPDATE` は KEY SHARE と衝突せず、状態更新どうしは引き続き直列化される。修正後は同じ検証で 0.4 秒・409 なし。

## ADR-033 整合性チェックは入れ子ループを使わない
- 決定: `checkIntegrity` の実行中だけ `enable_nestloop = off`（トランザクション内の設定）にする。
- 理由: 検査は組織の全行を集計する。作成・復元した直後の組織は統計情報に反映されておらず行数 1 と見積もられ、入れ子ループが行数の 2 乗以上に
  遅くなる（大きな組織がある DB で 500 注文の組織が 60 秒のタイムアウト）。ハッシュ結合なら件数に比例（83ms、51 万注文で 21 秒）。
  復元の最後にも実行するため、復元が大きな DB で失敗しないためにも必要。

## ADR-034 統計情報の更新を保守処理で補う
- 決定: 15 分ごとに、前回の ANALYZE 以降に 500 行以上変わった業務テーブル（許可リスト）を ANALYZE する。組織の復元の直後と、
  100 件以上の注文を確定した CSV 取込の直後にも ANALYZE の Job を登録する。
- 理由: 組織が少ない DB では全組織が統計の「よく出る値」に入り、後から作った組織は次の ANALYZE まで行数 1 と見積もられる。
  PostgreSQL の自動 ANALYZE は大きなテーブルでは変更率 10% まで走らない。負荷検証で、新しい組織の注文詳細 6→293ms、
  Fulfillment 一覧 1 ページ 2.5 秒になった。ANALYZE は業務データを変えず、1 テーブル数百 ms 程度。

## ADR-035 完了した返品は「届いた数」で返品済みを数える
- 決定: 返品可能数 = 出荷数 −（進行中の返品の申請数 + 完了した返品の到着数）。整合性チェックも同じ定義。
- 理由: 申請 2 個のうち 1 個だけ届いて検品・完了した後に残りが届いた場合、申請数で数えると新しい返品を受け付けられない（後から届いた品を
  記録する手段がない）。届かなかった分は完了時点で「返品されていない」ので、後から新しい返品として受け付ける。

## ADR-036 販売可能な棚と返品保留・破損の棚の間の移動は理由必須
- 決定: ロケーション移動で、移動元と移動先の種類が違い、どちらかが販売可能（pick）の場合は理由を必須にする（REASON_REQUIRED）。
  移動できる数量はどの種類でも「OnHand − 引当 − 調査中」。監査ログに移動元・移動先の種類を残す（理由の本文は在庫移動の行）。
- 理由: 返品保留（quarantine）は「後で移動/廃棄を判断」する置き場（RETURN_RULES.md）で、再確認後に販売可能へ戻す操作は必要。
  ただし売れる在庫が増える/減る判断なので、誰がなぜ行ったかを残す。画面は保留・破損の棚の最大数量を 0 と表示し API と食い違っていた。

## ADR-030 補足（Phase 10）
- ITF は 14 桁（ITF-14）のみ採用する（ZXing の ALLOWED_LENGTHS、BarcodeDetector 経路でも 14 桁未満を捨てる）。傾いた ITF が 14 桁中 10 桁を
  別の値として返すことを自動テストで確認したため。
- 手入力のコードは NFKC で正規化して照合する（日本語入力のまま打った全角の数字・英字・ハイフンも一致する）。バーコード登録時も正規化して保存。

## ADR-024 補足（Phase 10）
- 画面から扱うバックアップの上限を 2 つの設定に分けた: ファイル（gzip）`BACKUP_MAX_UPLOAD_MB`（既定 256MB）、展開後 `BACKUP_MAX_EXPANDED_MB`
  （既定 1024MB。以前は定数 1GB）。どちらも画面に表示。実測で約 10 万注文 = gzip 約 250MB のため、それより大きい組織は CLI。
- 写真ファイルが保存先に見つからない場合、backup-cli は警告して終了コード 1（`--allow-missing-files` で許容）、検証結果に欠落数を表示する。
